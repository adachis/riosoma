# Themes

Every design system in `design-systems/` is a Riosoma theme here, and all 52 of them switch the same way.  Between them they have 634 color schemes.  Everything in this folder except `rio-theme.js` is generated by `tools/build_themes.py`, so don't hand-edit it.  This document comes from `tools/themes-readme.md`.

## The contract

- **One stylesheet per theme.**  Load `themes/<theme>/theme.css` and only that one.  Themes reuse variable names (33 of them define `--accent`, each meaning something slightly different), so two at once would collide.
- **Color scheme: `data-scheme="<scheme>"`** on `<html>` or on any container.  Leave it off and you get the theme's default scheme.  Every scheme can be set by name, the default included.
- **Mode: `data-mode="<mode>"`**, only in the nine themes that have one (Bubble, Chillhop, Glitch, Holographic, Kicks, Magazine, Palette, Retro Game Manual, and Retro Neo Future).  It's usually `light` or `dark` layered on top of the scheme, and Retro Neo Future adds `crt`.
- **Surface: `data-surface="paper"`** on a container that should read as paper.  Only PSOne and Graffiti have one.
- **`data-theme="<theme>"`** on `<html>` is set by the switcher so Riosoma's own CSS can target a theme.  The theme stylesheets never use it.

Every stylesheet puts its rules inside `@layer rio.theme`.  Declare the app's layer order before loading a theme:

```css
@layer rio.defaults, rio.theme, rio.base, rio.components, rio.app;
```

Component rules in `rio.components` win over theme element rules.  The build removes every `!important` flag and drops universal rules that only change animation, transition, or scroll behavior.  Riosoma handles reduced motion.  Each manifest records the counts in `removedImportant` and `removedMotionRules`.

Each theme's `theme.json` lists its scheme, mode, and surface ids, so nothing has to be hard-coded.  Two themes also keep a system-specific attribute that isn't part of the contract: `data-invert` in System 7 (it swaps paper and ink) and `data-panel` in Industrial Retrofuturism.

## Prose scoping

Add `rio-prose` to help text, rich text, and published page containers.  Theme element styles apply to that container and its descendants.  Page styles from `html`, `body`, and `:root` apply to the container itself.  Scheme, mode, and surface attributes work on the container or an ancestor.  The added scope uses `:where(…)` so specificity does not grow.

Theme variables stay available throughout the app.  Rules that mix variables with element styling are split.  Theme classes, font faces, and keyframes keep their existing rules.  Plain app elements outside prose keep their unthemed styles, apart from inherited `color-scheme`.

The browser checks compare plain elements outside prose with an unthemed page.  They also check paragraph and heading fonts and text colors against the original design inside prose.  Both checks run for every theme's default scheme and a dark scheme when one exists.

## What the build guarantees

The build loads every theme in headless Chromium and fails if any of these break:

- An untagged page matches `data-scheme="<default>"` exactly.
- Every scheme changes something, and no two schemes in a theme are identical.
- Every mode changes something.
- A scheme set on a nested container resolves the same as it does on `<html>`.
- Every `--rio-*` semantic variable (below) matches `tools/semantic-baseline.json` in every scheme and mode.  Intentional foreground corrections update this snapshot.  Original decorative colors can have lower contrast.  Generated foregrounds must meet their guarantees.

- No stylesheet imports another stylesheet or requests a remote URL.
- Every rule stays in the rio.theme layer, and no declaration has an `!important` flag.
- Component colors win on buttons, links, headings, inputs, the body, and universal selectors.
- Every legibility variable resolves and meets its contrast guarantee in every scheme, mode, and surface, on the page root and nested containers.
- Every font family is open-licensed or a generic system fallback.  Each font file comes from a reviewed Google Fonts stylesheet, is listed in `remoteFonts`, and matches its checked-in SHA-256 fingerprint.  Missing or altered font files fail the browser build.

The results of the last run are in `verify-report.json`.

## Files

| Path | What it is |
| --- | --- |
| `index.json` | Every theme with its default scheme, scheme count, and modes |
| `<theme>/theme.json` | Schemes (id, display name, and light or dark appearance), default scheme, modes, surfaces, assets, and where the theme came from |
| `<theme>/theme.css` | The theme's tokens, bundled in the order the original system loads them |
| `<theme>/assets/` | Fonts and textures, not in git (see below) |
| `rio-theme.js` | A small vanilla switcher |
| `verify-report.json` | The browser check results |
| `FONT-LICENSES.md` | Families in use, verified licenses, copyright notices, and full license text |
| `FONT-ASSET-REMOVALS.md` | Retired bundled font files to remove from an older asset copy |

A scheme's `appearance` is `light` or `dark`, based on the page background the scheme actually renders.  In some systems the schemes only swap accent colors, so a scheme named Midnight can still be `light`.  That's accurate.

## Switching themes in the browser

```html
<script src="themes/rio-theme.js"></script>
<script>
  await RioTheme.setTheme('panic-play', { scheme: 'midnight' }); // loads theme.css, sets the attributes
  RioTheme.setScheme('lagoon');                                   // on <html>
  RioTheme.setScheme('ember', document.querySelector('#preview'));// just that subtree
  RioTheme.setMode('dark');                                       // only where theme.json lists modes
  const { themes } = await RioTheme.list();                       // index.json
</script>
```

`setTheme` loads the new stylesheet before removing the old one, so the page never flashes unstyled.  If you ask for a scheme or mode the theme doesn't have, it falls back to the theme's default.

## Fonts and textures

Fonts and textures stay out of git.  Pull the textures listed in the generated manifests from the original zips with:

```bash
python3 tools/fetch_theme_assets.py /path/to/design-system-zips
```

All fonts are self-hosted Google Fonts.  Download the files listed under `remoteFonts` in each manifest with:

```bash
python3 tools/fetch_theme_assets.py --remote-fonts
```

Both commands accept theme ids after the main argument to fetch a subset.  Downloads go into `assets/fonts/remote/`, and their SHA-256 fingerprints are checked before reuse.  Downloaded files never change the manifests.

Font substitutions live in `tools/font_substitutions.json`, with each theme's original CSS family, asset paths, replacement, role, and license.  Known Google Fonts aliases retain their canonical families.  Baloo 2, Micro 5, Source Serif 4, and VT323 were unmatched filenames in the input inventory, but their canonical families are open-licensed.  System 7's old files do not have one of the accepted licenses, including its CC BY-SA mono font, so they are replaced too.  Named operating-system fallbacks become generic stacks.

The allowlist in `tools/font-licenses.json` records Google Fonts metadata, license sources, weight and style coverage, and license text.  Review its source license file and Google's `isOpenSource` metadata before adding a family.  The stylesheet responses are committed under `tools/font-cache/`, and downloaded byte fingerprints are in `tools/font-cache/files.json`.  Normal builds never contact font services.  To review new font requests and pin their downloaded files:

```bash
python3 tools/build_themes.py --refresh-fonts --no-browser
python3 tools/fetch_theme_assets.py --remote-fonts --record-font-hashes
python3 tools/build_themes.py
node --test tools/font_license_gate.test.cjs
python3 -m unittest discover -s tools -p test_font_policy.py
```

`--no-browser` still checks families and file sources and regenerates the license document.  It permits absent binary assets while preparing a fresh copy.  The full build also checks every font's bytes.  `node tools/font_license_gate.cjs` runs the license gate by itself.  Font Awesome imports are dropped and recorded in `droppedImports`.  Riosoma supplies its own icons.

For an existing asset copy, regenerate the manifests, run `python3 tools/fetch_theme_assets.py --remote-fonts`, and copy each theme's `assets/fonts/remote/` directory back to the bundle.  Delete the retired paths listed in `FONT-ASSET-REMOVALS.md` from that bundle before shipping it.  The fetcher only extracts assets referenced by the current manifests.

```bash
asset_bundle=/path/to/your/theme-assets
python3 tools/fetch_theme_assets.py --remote-fonts
for font_dir in themes/*/assets/fonts/remote; do
  bundle_path="$asset_bundle/${font_dir#themes/}"
  mkdir -p "$bundle_path"
  rsync -a "$font_dir/" "$bundle_path/"
done
```

`node tools/measure_theme_fonts.cjs` emits comparable width, ascent, and descent measurements for the same heading text in every theme.  Run it before and after changing families to identify substitutions that need sizing adjustments.

## Rebuilding

```bash
python3 tools/build_themes.py                    # build, then run the browser checks
python3 tools/build_themes.py --no-browser       # build only
python3 tools/build_themes.py --update-baseline  # accept intended color changes
```

Every semantic color is compared against `tools/semantic-baseline.json`, so an accidental change fails the build.  When a change is intended, such as a new color scheme, rebuild with `--update-baseline` and review the one-line-per-theme diff before committing.

The browser checks need Node and Playwright.  Run `pnpm install && pnpm exec playwright install --only-shell chromium` once per machine to set them up.  Per-system exceptions (default scheme names, attribute renames, and the like) live in `tools/theme_config.json`, and each entry there explains itself.

## Semantic variables

Each theme keeps its own variable names (`--k-accent` in Kicks, `--neu-surface` in Neumorph, and so on), so every theme also maps them onto one shared set.  Riosoma's own components use these for design colors and the legibility tier below for readable foregrounds:

| Variable | Meaning |
| --- | --- |
| `--rio-bg` | Page background, the surface body text sits on |
| `--rio-surface` | Cards, panels, and sheets |
| `--rio-text` | Body text |
| `--rio-text-muted` | Secondary text |
| `--rio-border` | Default border and divider color |
| `--rio-accent` | The primary action color |
| `--rio-on-accent` | Text and icons on `--rio-accent` |
| `--rio-link` | Links |
| `--rio-focus` | Focus rings |
| `--rio-success`, `--rio-warning`, `--rio-danger`, `--rio-info` | Status colors |
| `--rio-font-body`, `--rio-font-display`, `--rio-font-mono` | Font stacks |
| `--rio-radius` | Default corner radius (`0px` in square-cornered systems) |

They follow the scheme, mode, and surface automatically, including on nested containers.  Each theme's `theme.json` records where every variable comes from under `semantic`.

**How the mapping works.**  `tools/semantic.py` picks each source in this order: an override in `tools/theme_config.json`, then whatever the theme's own `body`, `h1`, `code`, and `a` rules use, then a ranked list of common names (matched through system prefixes like `--k-`), and finally a fallback.  Link and focus fall back to the accent, display fonts to the body font, and missing status colors to plain defaults.  Candidates whose values aren't the right kind (a `--border` that's really `2px solid …`, say) are skipped.  To change a mapping, add an override and rebuild.

**Contrast notes.**  The build reports pairs below WCAG guidelines, like body text under 4.5:1 or accent text under 3:1.  Right now that's FunOS's Flag scheme (4.3:1) and some pastel accents with white text in 22 themes, all as the original designers chose them.

## Legibility tier

The `--rio-aa-*` variables keep text, icons, focus rings, and control boundaries readable.  Use them wherever contrast matters.  The semantic `--rio-text`, `--rio-text-muted`, and `--rio-on-accent` tokens also resolve to their generated foregrounds.  Original theme variables and semantic fill colors stay unchanged.  The `--rio-ink` token retains the original body color for derived fills and decoration.

Text is checked on page, card, raised, sunken, and interaction fills.  When those fills leave no readable foreground, generation reduces the shared tint strengths from the maximum percentages in `tools/theme_config.json`.  The generated `--rio-legible-*-tint` values follow each scheme, mode, and surface.

| Variable | Minimum contrast |
| --- | --- |
| `--rio-aa-on-accent` | 4.5:1 against `--rio-accent` |
| `--rio-aa-text` | 4.5:1 against page, card, raised, sunken, hover, pressed, and selected backgrounds |
| `--rio-aa-accent-text` | 4.5:1 against both `--rio-bg` and `--rio-surface` |
| `--rio-aa-text-muted` | 4.5:1 against page, card, raised, sunken, hover, pressed, and selected backgrounds |
| `--rio-aa-link` | 4.5:1 against both page and card backgrounds |
| `--rio-aa-focus` | 3:1 against both page and card backgrounds |
| `--rio-aa-border` | 3:1 against both page and card backgrounds for form-control boundaries |
| `--rio-aa-success-text`, `--rio-aa-warning-text`, `--rio-aa-danger-text`, `--rio-aa-info-text` | 4.5:1 against page, card, raised, sunken, hover, and pressed backgrounds |
| `--rio-aa-on-success`, `--rio-aa-on-warning`, `--rio-aa-on-danger`, `--rio-aa-on-info` | 4.5:1 against the matching status fill |

Passing design colors stay unchanged.  Derived fills require an additional 0.1 margin for browser rounding.  Other colors keep their OKLCH hue and change lightness by the smallest amount that reaches the target plus 0.1.  Chroma decreases only as needed to stay in sRGB.  Translucent colors are checked over each background.  An adjusted translucent color starts from its visible color on the page and becomes opaque.

For text on a fill, the build tries the original on-color, body text, and page color in that order.  It then adjusts the original on-color before trying black and white.  A status without its own on-color starts from `--rio-on-accent`.

Each manifest records `legibility` as scheme → mode → variable → value, including foreground colors and tint percentages.  The `default` mode means no mode attribute.  `legibilitySurfaces` adds a surface level for surface overrides.  `legibilityAdjusted` counts color adjustments across those combinations, including explicit default modes.  `legibilityOnColors` records the status on-color sources.

The build resolves colors in Chromium, writes the tier inside the theme layer, and reloads it for verification.  Inherited surface colors let surface-only containers follow their scheme.  Set a nested mode on the same container as its scheme.  `--no-browser` preserves the last generated tier and cannot refresh it.  The defaults layer provides semantic aliases for older stylesheets, without a contrast guarantee.

The tokens package exports `contrastRatio(a, b)`, `adjustForContrast(color, backgrounds, target)`, and `legibleOn(fill, candidates, target)` for custom brand colors.  Inputs are opaque three-digit or six-digit sRGB hex colors.  Results are six-digit hex colors, or `null` when the required contrast cannot be reached.  Adjustment requires the extra 0.1 margin.  Candidates for `legibleOn` are the original on-color, body text, and page color in that order.  Both implementations must match the shared vectors in `tools/legibility-vectors.json`.

## Fixes to the original design systems

The build corrects these without touching `design-systems/`, so every fix is visible in `tools/theme_config.json` or `tools/build_themes.py`:

- **mOS:** the default `:root` block came after the Light scheme and silently overrode it on `<html>`.
- **Seven systems** (Art Nouveau, Bubble, Colorful Minimalist, Fashion, Gamer, Retro 90s, and Shabby Chic): an untagged page didn't match the named default scheme.  Untagged now always equals the default.
- **Many systems:** a scheme set on a nested container kept stale colors, because some variables were only calculated at the page root.  Nested schemes now resolve exactly like `<html>`.
- **Groovy:** a light scheme nested inside a dark one inherited `color-scheme: dark`.
- **Panic Play Midnight:** near-black text on a navy page (1.2:1) and white text on yellow buttons (1.6:1).  It now uses light ink and dark button text.
- **Chillhop modes:** a root-only specificity boost let nested schemes override Dark mode.  Nested scheme and mode combinations now use the same precedence as the page root.
- **Steampunk's default scheme** didn't set its accent hue, so it picked up the parent scheme's accent when nested.
