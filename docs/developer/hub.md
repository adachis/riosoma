# Hub operations

`apps/hub` is a Worker with R2 `FEED` (`riosoma-feed`) and D1 `STATS` (`riosoma-hub`). Tests use Wrangler's Miniflare runtime and intercept every outbound GitHub request. The legacy Workers pool currently requires a different Vitest major version from this workspace, so it is not installed.

## Building and testing

The hub is its own pnpm workspace, outside Riosoma's, the same way as the Zapier app.  Wrangler and the Workers types are listed only in `apps/hub/pnpm-lock.yaml`, so Riosoma's own install and image never fetch them.  Install the repository first with `pnpm install` at its root, since the hub reuses its TypeScript, ESLint, and Vitest, and its Worker imports schemas from `packages/contracts`.  Then run `pnpm hub:test` from the root, which installs `apps/hub` from its own lockfile, then typechecks, lints, builds, and tests it.  From `apps/hub`, the same steps are `pnpm install` and `pnpm test`.  CI's `check` job runs `pnpm hub:test`, the `security` job scans the hub's lockfile, and Dependabot proposes updates for it separately.

## Deploying

Before a deployment, provision the bucket and database, apply `apps/hub/migrations/`, and supply the real D1 database ID in a deployment configuration outside the committed file. Supply the account ID through `CLOUDFLARE_ACCOUNT_ID`. Set `GITHUB_TOKEN` (issue read/write in `adachis/riosoma`) and `STATS_TOKEN` as Worker secrets. Create the `bug` and `from-installs` labels in the repository. After `pnpm install` in `apps/hub`, `pnpm --dir apps/hub run deploy` from the root runs Wrangler; this unit does not deploy or provision anything.

`BUG_REPORTS_PER_INSTALL_DAY` defaults to 10, `BUG_NEW_ISSUES_PER_DAY` to 20, and `BUG_COMMENTS_PER_DAY` to 50.  All three use UTC days and accept nonnegative integers, and zero disables that allowance.  Claims and reservations are transactional in D1, including concurrent fingerprints.  Install IDs are self-reported random UUIDs, not proof of identity, so the global caps bound what reaches GitHub even if someone rotates them.  The two defaults together stay under the number of content-creating requests GitHub accepts in a minute, so a burst cannot push genuine reports into `review`.  Statistics use a timing-safe comparison and summarize the previous completed week, which installs report during the current week.

The `WRITE_LIMITER` rate limit binding also counts `POST /bugs` and `POST /telemetry` per network address, five a minute for each, and answers 429 beyond that before anything is read or stored.  An IPv6 address counts as its /64.  Nothing has to be created in the account for the binding, and its `namespace_id` only has to be unique within the account.  The binding does have to be in the configuration that gets deployed.  Copy the `ratelimits` entry into the deployment configuration before deploying, because both routes answer 503 without the binding.  Bring that file's `vars` in line with the committed ones at the same time, since a `BUG_NEW_ISSUES_PER_DAY` left at an older value overrides the default, and add `BUG_COMMENTS_PER_DAY` beside it.  The limiter keeps its counters in memory, so the hub stores no IP or header data, and request observability stays disabled in its configuration.  The address limit slows one caller and cannot stop someone who rotates addresses, which is why the global caps stay.

Everything relayed is published inside code blocks: the description, version, platform, and fingerprint in the issue, and the report count and versions in the daily comment.  Mentions, cross-references, links, and Markdown in a report therefore stay plain text.  A report's version must be a release version or `custom`, and a fingerprint keeps at most 20 versions.  `0002_bug_comment_days.sql` adds the table behind the comment cap.  Apply it before deploying, because reports answer 503 without it.

An issue-cap overflow stays `queued`, with its count and versions.  Nothing files it later on its own.  An install that was answered with a pending report only looks the fingerprint up afterward, and a lookup never files, so a queued report becomes an issue only when another report with the same fingerprint arrives on a day with a slot left, or when a maintainer files it.  Someone who spends the day's slots early therefore keeps that day's genuine new reports queued, and no setting here prevents that for a caller who rotates addresses.  Check the `queued` rows in `bug_reports` regularly, and on any day the cap was reached.  For each genuine one, open the issue by hand, then attach its issue number and URL, set `last_comment_day` to that day so later reports can add comments, and mark it `filed`.

If GitHub may have accepted a request whose reply was lost, the fingerprint stays `review` (or `filing` after a process interruption).  Reconcile it against GitHub before manually marking it `filed` the same way, or returning it to `queued`.  There is no automatic retry that could open another issue.  Comment claims likewise remain spent after a failed call until the next UTC day.

`GET /bugs/:fingerprint` returns the accepted report's issue URL with 200, or a null URL with 202 while it is pending.  Unknown fingerprints return 404.  This lookup never increases report counts, consumes daily quotas, records versions, files issues, or posts comments.  Installs retain the accepted fingerprint separately until an admin refreshes and records the issue URL.  Pending lookups do not retry queued or ambiguous issue creation.

The Worker never signs a feed. Release jobs use `tools/sign-feed.mjs` and upload its envelope as `updates.json`. Keep private signing material only in the release job's secret environment. Public keys ship separately in the server and updater. No production keys are part of this unit.
