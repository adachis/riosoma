# Named-function compilation

The formula package accepts a database's named-function definitions as the fifth argument to `resolve`. Each definition has a name, an ordered list of parameter names, and a body in the formula language. For example, `NET(amount, discount)` can use the body `amount * (1 - discount)`.

Function and parameter matching ignores capitalization. Parameters can be written as bare names or brace references. Bodies can call built-in functions and other named functions. They cannot capture fields or table references: pass those through parameters. Built-in names are reserved, and duplicate function names, duplicate parameters, unknown calls, wrong argument counts, and direct or indirect recursion are rejected across the entire registry, including unused definitions.

`prepareNamedFunctions` validates and snapshots a registry and exposes its canonical names for completion. Its `expand` method replaces named calls with parameter-bound bodies. `resolve` resolves all supplied field arguments first, then expands calls. The ordinary `check`, `references`, `readsRecords`, `evaluate`, and `compileSql` APIs consume the resulting AST. Parameter types are inferred at each invocation. Type checking applies where a parameter is used; unused parameters do not evaluate their arguments. Lazy branches remain lazy. Every parameter occurrence gets its own AST nodes so a lookup can read as a list in one place and one value in another.

The registry is supplied explicitly, with no global cache or cross-database lookup. Definitions are limited to 100 per registry, 32 parameters, 64 characters per name, and 10,000 characters per body. Expansion stops at 10,000 visited nodes or a depth of 256. These bounds apply before either execution engine receives the expanded AST. SQL retains parameterized literals and returns `null` for unsupported operations, using the existing JavaScript fallback.

The differential suite compares named calls in PostgreSQL and JavaScript across seeded formulas, blank values, lazy errors, dates, lookup lists, and numeric overflow. Separate unit tests cover validation, diagnostics, dependencies, registry isolation, and expansion limits.

## Database integration

Migration 0090 stores definitions by database, with a case-insensitive unique name, creator and last editor, timestamps, and a revision. The `namedFunction.create`, `namedFunction.update`, and `namedFunction.delete` commands require database editing access (editors, creators, and owners). Updates and deletes supply the current revision. The command bus records audit events, undo history, and realtime changes. Schema reads expose definitions through AccessScope; internal field preparation loads only the registries belonging to those fields' databases so AccessScope can inspect expanded dependencies before deciding which fields are visible.

Field preparation, formula field creation, request formula filters, and client evaluation supply the registry explicitly. Stored expressions retain named calls and stable field references; expansion is confined to execution plans. Definition changes recheck the database's fields and invalidate their existing dependency graph, snapshots, computed overrides, and joined tables. Realtime changes carry the new registry entry and field metadata so clients recompile and refresh rows. Missing calls and changed signatures become formula errors. The formula editor completes names with parameters and descriptions, preserves calls when displaying existing expressions, and translates diagnostics. Rio's schema tool includes definitions.

Deleting a used definition requires `confirmUsed` after a refusal naming the fields and named definitions that call it.  A registry must remain valid: deleting or renaming a function referenced by another named definition requires updating that definition first.  Callers in formula fields may become broken after a confirmed delete or rename, and undo restores the definition and recomputes them.  This preserves the compiler's whole-registry validation without making unrelated formulas fail because one saved definition is invalid.

Mutations and undo trace callers through named definitions, formula fields, relational fields, and joined projections into record rules.  Changing an input to a rule requires the same schema permission, unrestricted record access, and visible condition fields as administering that rule.  Unrelated functions still require only database editing access.  Definition mutations share the rule-edit lock and load a fresh AccessScope before authorizing the write.

Database archives capture definitions through AccessScope for snapshots, duplicates, and organization templates.  Restore validates the registry and creates definitions through the command bus in dependency order before formula fields.  Names, parameters, bodies, and descriptions stay intact, and restored definitions receive new IDs.  Older archives without definitions remain readable.  Automatic snapshots use the organization owner's archival access, as organization backups do.

## Management and external access

The database sidebar opens `/databaseId/named-functions`; `/databaseId/named-functions/functionId` selects a definition, and `new` opens creation. The body reuses the formula editor with parameter suggestions and whole-registry validation. The test panel evaluates sample formula expressions with the draft registry without writing records. The screen uses database editing access, command revisions, inline refusals, and a confirmation naming transitive formula and function callers.

REST v1 exposes GET and POST at `/api/v1/databases/{databaseId}/named-functions`, and PATCH and DELETE at its `/{functionId}` child. Updates replace a definition and require its revision; deletes require a revision and optionally `confirmUsed`. Reads use `schema.bases:read`; writes use `schema.bases:write` and the existing scoped commands, and return an undo group in the body and header. MCP provides `list_named_functions`, `create_named_function`, `update_named_function`, and `delete_named_function` through the same implementation. The SDK exposes `client.namedFunctions`.

The named-functions help module links {{ui:field.formula.expression}} and {{ui:field.formula.suggestions}}. Chromium coverage exercises creation, formula calls, recomputation after edits, and delete warnings. Standalone archive serialization and restoration use the same writer and dependency-ordered restore as database duplication. Organization archives preserve definitions and their authors, restoring them before formula fields.
