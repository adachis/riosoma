# Data Source

How Riosoma copies tables from other systems, keeps them in step, and lets people correct what the source gets wrong without touching the source.  The request and message shapes live in `packages/contracts/src/sources.ts` and `source-refs.ts`, and that code wins where the two disagree.

## The pieces

- A **source** is one connection to an outside system: a PostgreSQL, MySQL, SQL Server, Oracle, or Firebird database, a Snowflake, BigQuery, Databricks, MotherDuck, or Teradata warehouse, a ClickHouse, Trino, or Apache Druid analytics engine, files at a web address or in an S3-compatible bucket, a web API that answers in JSON, a MongoDB database, the sheets of Google spreadsheets, the tables of Airtable bases, the lists of SharePoint sites, the sheets of Excel workbooks in SharePoint or OneDrive, the tables of a Dataverse environment, an RSS, Atom, or JSON feed, or an incoming webhook that other systems post to.  Admins with the Data Sources role set sources up once for the whole organization.
- A **synced table** is an ordinary table in a database whose records come from one table, view, or query in a source.  Its **source fields** copy the source's columns.  People can add their own fields beside them (notes, links, formulas, attachments), and those behave like any other field.
- An **override** is a local value in a source field's cell.  Everyone sees the override instead of the source's value, which stays on record beside it.  Overrides never flow back to the source.

## Sources

- Stored in `rio_app.sources`: organization, name, description, kind, the connection settings (JSON), the sealed secrets, who may use it (`admins`, or `creators` for anyone who can add tables), and the last test's result.
- **Secrets are write-only.**  The browser sends them once.  The server seals the whole set with the instance key (AES-256-GCM, `secrets.ts`), using `source:<sourceId>` as associated data so a sealed value can't be moved to another source.  Responses say only which secrets are stored.  Secrets never reach logs, errors, or the change history.
- **Testing** climbs one step at a time and stops at the first failure: the SSH tunnel (when there is one), name resolution, the TCP connection, TLS, authentication, and a trivial query.  Each failed step answers with a message key that says what usually fixes it, plus the driver's own words for people who know the system.  Saving doesn't require a passing test, since a source can be down while it's being set up.
- A source can't be deleted while synced tables use it.

## Connectors

`packages/connectors` holds one connector per kind behind one interface: test, list objects, describe columns, preview, find key candidates, and read rows in batches.  The rest of Riosoma never touches a driver.

### The connector service

The kinds whose drivers the server doesn't otherwise use run in a service of their own, so the server's image never carries those drivers: MySQL, SQL Server, Oracle, Firebird, Snowflake, BigQuery, Databricks, ClickHouse, and MongoDB (`SERVICE_KINDS` in `packages/connectors/src/service/protocol.ts`).  Their code lives in `packages/connector-drivers`, which only the service in `apps/connector-service` depends on.  Kinds whose driver the server uses anyway stay in the server: PostgreSQL and Redshift on `pg`, which Riosoma's own database uses, and MotherDuck and DuckDB files on DuckDB, which the file sources use.  So do the REST, app, GraphQL, OData, file, feed, sheet, search, graph, and metrics sources, and the admin-installed drivers below, which load from `RIOSOMA_DRIVERS_DIR`.

- **In the server**, each of those kinds is registered as a connector that implements the same interface by calling the service (`createServiceConnector` in `service/client.ts`), so nothing above the registry knows the difference.  `apps/server/src/sources/connector-service.ts` finds the service: at `RIOSOMA_CONNECTOR_SERVICE_URL`, or, running from a source checkout without it, as a child process the server starts on a loopback port with a token made for the run.  `/healthz` and `/readyz` report it as `connectors` and stay healthy without it.
- **The API** is JSON over HTTP on the internal network: `POST /v1/<kind>/test`, `objects`, `describe`, `preview`, and `keys` answer `{ "result": ... }`, and `read` streams newline-delimited JSON, a line per batch and a last line that says the read ended or why it failed, with blank lines to keep a quiet read's connection open.  Live tables' sessions open with `POST /v1/sessions`, run `describe` and `select` at `/v1/sessions/<id>/...`, and close with `DELETE`.  Values JSON would lose, such as dates, bytes, big integers, and numbers that aren't finite, travel tagged (`encodeValue`), since a session answers with the driver's own values for the server to convert.
- **Failures** cross as the connector error's message key, parameters, and the connector's own sanitized words.  Anything else a driver throws becomes a plain `sources.sync.read` with no words at all, and the service also removes any of the request's secrets a connector repeated.  A service that can't be reached, refuses the token, or drops a read partway fails the call with `sources.service.unavailable`, and a test reports it as its first step, `driver`, rather than throwing.
- **Cancellation** follows the caller: a call's abort signal, or a read the server stops taking batches from, closes the request, and the service aborts the connector's own signal and stops reading.  Each batch waits until the server took the one before.
- **Secrets** travel only in request bodies, never in an address or a header other than the shared bearer token, and the service logs only a request's method and path and an error's type.
- **The private-network rule** travels with every call (`network`: production, the operator's setting, and whether the call comes from the public demo), and the service builds the same guard the server would (`privateNetworkGuard` in `network/private.ts`), so ClickHouse and MongoDB look every host up under the same rule.  The server still checks a source's hosts before it's saved or tried.
- **The token** is the operator's `RIOSOMA_CONNECTOR_SERVICE_TOKEN`, or one the server generates on first start into `RIOSOMA_CONNECTOR_SERVICE_TOKEN_FILE`, which the service reads from the storage both mount.  The service waits for it, isn't ready until it has one, and reads the file again when a token doesn't match.

`apps/connector-service/src/contract.test.ts` drives every kind the service runs through the server's connector and the real service on a port of this machine, against the same fixtures its own tests use, and `apps/server/src/sources/connector-service.test.ts` covers the server's side: an unreachable service, failures, cancellation, live sessions, the rule, and where secrets go.

- **Files** (`file-url` and `bucket`) share one connector on DuckDB: each call downloads its files through the server's guarded client into a private temporary directory (never DuckDB's own fetcher, which the private-network rule can't reach), reads them with DuckDB locked into that directory, and removes it.  CSV, TSV, and workbook columns take the upload importer's types, and a bucket prefix also offers one object per format that reads every such file together.
- **APIs** (`rest`) offer their endpoints as objects, each a path under the base address with its records' place in the answer and its paging style (page numbers, offsets, cursors, next-page addresses in the body or the `Link` header).  Every request is a GET through the same guarded network file sources use, at the source's pace (5 a second by default), waiting out a 429 or 503's Retry-After within bounds, and a next page on another origin is refused.  OAuth's token request is the one POST, and it follows no redirect.  Records flatten to dotted columns and take the file sources' type rules, a sync past an endpoint's page or record limit fails rather than removing records, and the test climbs to finding the records and reading a second page.
- **MongoDB** (`mongodb`) offers one database's collections and views.  The server is named by a connection string, sealed since it can hold a password, or by a host with an optional user and sealed password, with TLS (on for `mongodb+srv` unless the string says otherwise), a private CA, an auth source, and an SSH tunnel to one server.  Describing samples up to 1,000 documents with `$sample` (the first ones when the server can't), puts them in `_id` order, and flattens them by the API sources' rules: `ObjectId` reads as hex text, dates as instants, `Decimal128` and 64-bit integers past 2^53 as exact text, and binary data as unsupported.  `_id` is always the offered key.  Reads use a cursor with a batch size, a projection of the chosen top-level fields, and the call's deadline and abort signal, and a synced table's optional filter (admins only) is a JSON query document that never runs JavaScript (`$where`, `$function`, and `$accumulator` are refused).  Every name the driver looks up, every address a connection string or a replica set names outright, and a tunnel's bastion are held to the private-network rule, and the test climbs to listing collections and reading one document.
- **Google Sheets** (`google-sheets`) offers the sheets of the spreadsheets a source lists, each by its spreadsheet's ID and its own sheet ID, with their names as labels, so renaming either keeps a synced table reading.  It signs in as a service account whose JSON key is sealed: the connector signs a JWT for the read-only Sheets scope with Node's own crypto and trades it at Google's token address, whatever the key names, for a token kept in memory until it nearly expires.  The account's address is copied from the key into the settings when a source is saved, so the form can show whom to share spreadsheets with.  A sheet's header row (the first unless set) names its columns, blank and repeated names get the file sources' treatment, and a reserved `Row number` column is offered last as a key, with a warning in the wizard.  Rows are read unformatted with dates as the sheet formats them, in requests of at most 500,000 cells, and take the file sources' type rules.  Requests go through the guarded network at one a second for each service account, Google's reading quota, waiting out a 429 or 5xx within bounds.  A column that has gone from the header fails the sync.  The test climbs to the token exchange, listing each spreadsheet's sheets, and reading the first sheet's header.
- **Airtable** (`airtable`) lives in the server, since it reuses the Airtable import's client and field mapping.  A sealed personal access token signs in, and the settings name the bases it offers (at least one, at most 50), which an admin checks in a list the token's bases fill, from one paged listing.  It offers only those bases' tables, each by ID with its name as a label, and refuses a table in any other base before asking Airtable, so the rest of what a token reaches never shows up in Riosoma.  The client reaches Airtable through the guarded network.  Every request to a base (a sync's read and its linked names, previews, and tests) goes through that base's one limiter, evenly spaced at four a second with the API sources' pacing, under Airtable's five, and counts against the import's limiter for the base too.  A 429 pauses the base as long as Airtable asks, 30 seconds unless it says otherwise.  A call waits out a pause when it leaves the call 10 seconds for its requests, which a sync's read (20 minutes) does and a preview or a test (30 seconds) doesn't, and otherwise ends at once with `sources.airtable.slowDown`, which the next sync gets past.  Fields take the import's types, except that links hold the linked records' names as text (read from the linked table's primary field), attachments hold file names, and computed fields hold Airtable's values typed by their result.  Each column carries notes saying how it comes across, which the wizard shows.  `Record ID` is the key.  Reads ask only for the fields a table holds, a field that has gone fails the sync, and nothing is ever written.  The test climbs to checking the token, listing the first chosen base's tables, and reading a first page.
- **Microsoft 365** (`sharepoint-list`, `excel-online`, and `dataverse`, in `packages/connectors/src/microsoft/`) sign in as one Entra app with the client credentials grant: the settings name the tenant and the app's client ID, the `clientSecret` secret is the rest, and the token for each service's `/.default` scope is kept in memory until it nearly expires.  Every request goes through the guarded network at ten a second for each app and service, waits out a 429 or a busy answer as long as Retry-After asks, within bounds, renews a refused token once, and follows `@odata.nextLink` only on the first page's origin.  Addresses are held to Microsoft's own hosts by the contract (`*.sharepoint.com` and `*.crm*.dynamics.com`), so a token never goes anywhere else, and a site or workbook address is kept encoded one way, so it reads back the same.  A **SharePoint list** source names sites by address (`sharePointSiteOf` finds a site in any address inside it), resolves each through Graph, and offers the lists that aren't libraries, hidden, or system lists, by ID with the site's Graph ID as the schema.  Columns come from each list's column definitions, named as shown: text (rich text as Markdown), numbers and currency, yes or no, dates (a date-only column, which SharePoint keeps as the instant of the site's midnight, reads as the nearest day), choices as select fields with their choices, hyperlinks, and calculated columns by their output type, while people, lookups, and managed metadata hold names as text, read from the items themselves or, when an item carries only a lookup ID, from the site's people list and the linked list.  `Item ID` is the key.  An **Excel workbook** source names workbooks by the address Excel's Copy path gives, finds each one's site, library (by the library's own address), and file through Graph, and downloads it, since Graph's workbook API refuses an app's sign-in.  Each call reads the file with the file sources' engine and the server's workbook reader in a private directory it removes, and a workbook's sheets are offered by name with the file's drive item ID as the schema, so a moved file keeps its synced tables once the source names its new address.  A **Dataverse** source reads one environment's Web API with a token for the environment's own address.  It offers the tables that aren't private or intersect tables and that are custom or offered in Advanced Find, by logical name, types columns from the attribute metadata and each type's own definitions (formats, precision, and choices' labels), reads choices and lookups by the formatted values Dataverse annotates rows with, and keys each row by its primary ID, `Row ID`.  A 401, or a 403 saying the app isn't a member of the organization, means the app isn't an application user, and any other 403 means its role lacks a privilege.  None of the three writes, and none reads live.
- **Feeds** (`feed`) read RSS 2.0, RSS 1.0 (RDF), Atom 1.0, and JSON Feed 1.1 through the guarded network, parsed with `fast-xml-parser` after the document's own DOCTYPE is removed, so no entity a feed declares is ever expanded or fetched.  A feed offers one object, `items`, with fixed columns: `id` (the key: `guid` or `id`, else the link, else a digest of the item), `title`, `link`, `author`, `published`, `updated`, `summary`, `content`, `categories`, and `enclosure`.  Addresses resolve against `xml:base` and the answer's own address.  Titles and summaries become plain text, and content becomes rich text Markdown through a lenient HTML reader that keeps only what rich text can say, so scripts, styles, frames, and unsafe links never survive.  Items that share an ID keep the first.  A read sends the `ETag` and `Last-Modified` the last finished sync kept (`fetch_state`), and a `304` ends it with `NotModified`, which the sync records as a success with nothing changed.  Changing a feed's address or its headers clears `fetch_state` for its tables, since validators answer only for the request they came from.  A feed's table syncs every 15 minutes to once a day, or only when asked.
- **Webhooks** (`webhook`) live in the server, since their data does: see Incoming webhooks below.
- **Analytics engines** (`clickhouse`, `trino`, and `druid`) run on the warehouses' shared frame (`warehouses/frame.ts`) and answer over HTTP, HTTPS unless a source turns it off, always checking the certificate and its name.  A pasted address fills in the host, port, and HTTPS.  ClickHouse uses `@clickhouse/client` and asks for nothing a `readonly=1` user can't: it sends no settings, so 64-bit integers and decimals are read with `toString` and date-times with `toTimeZone(…, 'UTC')`, and a database the user can't use is reported at the test's query step.  It hides stream engines (Kafka and the like) and pages a read by 50,000 rows, after the last row read, in the order of the sorting key's plain columns and the sync's key, with `LIMIT … WITH TIES` so ties stay on one page, when every key column can carry a cursor (never empty, and a type ClickHouse binds exactly), and by `OFFSET` over a fixed order otherwise.  A table in the Replacing, Collapsing, VersionedCollapsing, Summing, or Aggregating MergeTree families (by `system.tables.engine`, replicated and `Shared` variants included) reads with `FINAL`, so unmerged versions of a row never reach a sync.  Trino speaks the client protocol itself (no client library): `POST /v1/statement`, then each `nextUri`, every request under the session's abort signal and retried on 502, 503, and 504.  It keeps a password or a token off plain HTTP, refuses a `nextUri` on another origin so the sign-in never leaves the coordinator, signs in outside the catalog, checks the catalog and schema at the query step, reads a `bigint` as `varchar` and an instant with a zone `AT TIME ZONE 'UTC'`, and names rows' fields in their JSON.  A query left early, closed, or aborted, even one still queued or planning, is canceled with a `DELETE` of its current `nextUri`, and no request follows it.  Druid asks for `arrayLines` with name and type headers and fails an answer without its closing blank line, tells a refused sign-in (401) from one that may not run SQL (403), passes a cluster with no visible datasource with a note, and reads a `BIGINT` as `VARCHAR`.  It pages by keyset on `__time` (`WHERE __time > last ORDER BY __time LIMIT n`), and when a full page ends, it drops that page's rows at its last `__time` and reads every row at that time in one request, so no `OFFSET` ever splits rows that share a time.  More than 1,000,000 rows at one `__time` stop the read with a plain error.  A query without a `TIMESTAMP` `__time`, or one Druid won't sort by it, reads in one streamed request.  Trino and Druid talk through a `fetch`-shaped function over each session's own `node:http` agent, and ClickHouse through the client's `http_agent`, which is how a private certificate authority and the server's host guard reach the sockets.  The server holds all three to the private-network rule MongoDB, files, and APIs follow (`sources/analytics.ts`): a literal private address or `localhost` is refused before a source is saved or tested, and every name is resolved through the guard, which pins the connection to the checked addresses.  Error bodies that reach a detail keep their first 200 characters as plain text.  None of the three declares unique keys, and none reads live: the live framework's translation and parameters are written for the three SQL dialects.
- **Oracle** (`oracle`) uses `oracledb` in thin mode only, so no Oracle client is installed, and the package's install script stays off.  A source names a host, port, and service, or an Easy Connect string that `parseEasyConnect` holds to one host and a service with an optional server type and instance.  Every host, the TLS name included, has to pass `isHostName` (one DNS name, IPv4, or IPv6 address), and the connector builds the connect descriptor from those checked parts (`oracleDescriptor`), so the driver never reads text a person typed and can't take a host list, a descriptor, or parameters from it.  The driver follows a listener's redirect on its own, so the connector wraps the driver's transport (`NTTCP.prototype.connect`) and refuses any connection a redirect opens.  TLS (TCPS) has no `prefer` and no `require`, since the driver always checks the chain, and a `tcps://` string means `verify-full` unless the source says otherwise.  The driver does TLS itself, renegotiation after a listener's handoff included, with a wallet (`walletContent`) built from the source's CA and the `wallet` secret's certificates and key (decrypted with `walletPassword`), or a throwaway key when there's none, since it loads trusted certificates only beside one.  `verify-ca` needs an authority of the source's own, pasted or in the wallet (`requiredSecrets` asks for the wallet when none is pasted), since the platform's authorities with no name check would pass any certificate they sign.  The driver checks the name against the descriptor's host, so the descriptor names the database's host (or `serverName`), and a route token in the driver's HTTPS proxy setting keeps it from resolving that host itself.  The connector's wrapper on the driver's `ntConnect` opens the one socket the route allows, in this process, straight to the host or the SSH tunnel, so there's no local listener for anything else to take, and refuses a second socket for the route.  Both wrappers check at load that the driver still has the methods they wrap.  Every call reads in `SET TRANSACTION READ ONLY`, which covers the session's own changes but not a function's autonomous transaction or a database link, so the help asks for a login with only `CREATE SESSION` and `SELECT`.  Each round trip has the statement timeout as the driver's `callTimeout`, which interrupts the server, and a close breaks a call in flight first.  `NUMBER` and LOBs are fetched as text, one row's `CLOB` at a time, dates and timestamps are projected with `TO_CHAR` (with `SYS_EXTRACT_UTC` for zoned ones) so the driver's own time zone never shifts them, and `NUMBER(p, s)` with a scale reads through a format that keeps every declared digit.  `DATE` maps to a date with time, since it carries one.
- **Firebird** (`firebird`) uses `node-firebird`, unmodified, for Firebird 3, 4, and 5.  The database is a path or an alias.  The connector takes the driver's `attach` apart into its connect and attach steps (`attachFirebird`).  With `wireCrypt: 'required'` (the default) the driver offers only SRP (SHA-256, then the variant the server names, as Firebird 3's default `Srp` needs), an instance wrapper on `sendOpContAuth` refuses to answer a request for Legacy_Auth, and the attach, whose request can carry the password on old protocols, goes out only once the server accepted SRP on protocol 13 or later and `op_crypt` has turned wire encryption on.  The driver's automatic reconnect, which would sign in again unchecked, is off twice over: the options say the connection is pooled, and a close handler that runs before the driver's marks it detached.  The connector checks at load that the driver still has the steps it drives, and `RDB$GET_CONTEXT('SYSTEM', 'WIRE_ENCRYPTED')` confirms the result afterward.  `enabled` signs in however the server asks.  Columns are described by preparing the statement, never executing it, with types named from the prepared statement's storage (`numeric(18,4)`, `int128`, `decfloat(34)`, `time with time zone`).  Every call reads in one read-only snapshot (`readOnly`, repeatable read), which Firebird extends to a procedure's autonomous transactions, with the statement timeout on Firebird 4 and later, and rows stream with backpressure.  Integers and exact decimals arrive as exact text (`NUMERIC_MODE_STRING`), text BLOBs as text, dates and times cast to text on the server (zoned instants `AT TIME ZONE 'UTC'`), and `DECFLOAT`, which the driver can't read, as its text.  The driver fills a missing password from the environment or with Firebird's well-known default, so the connector passes every option itself and refuses to connect without a stored password, and a close cancels a statement in flight and drops the socket rather than waiting on the server.
- Both sync as copies only.  The live framework's translation is written for the other three dialects, so `LIVE_SOURCE_KINDS` doesn't name them.
- **Postgres** reuses `@riosoma/db`'s connection layer, so every security setup the app supports for its own database works for sources too: TLS modes and private CAs, client certificates, Entra, RDS IAM, and Cloud SQL IAM tokens, and SSH tunnels with pinned host keys.
- **Types** map to field types once, in the connector: integers and decimals to number (with precision), text types to single line or long text by declared length, booleans to checkbox, dates to date, timestamps to date with time, JSON to long text.  Binary and other types Riosoma can't hold are offered as unsupported and left out.  Each column also lists the other types it converts to cleanly.
- **Values** arrive already in Riosoma's forms (numbers, `YYYY-MM-DD`, ISO instants in UTC, text), so the sync engine never guesses.
- **Queries** (admins only) run inside a read-only transaction where the system has one, wrapped as a subquery so only one statement can run, with a statement timeout.  Sources should still use a read-only login.
- Every call takes an abort signal and a deadline.

## Admin-installed drivers

Teradata, Db2, and Informix use the driver catalog in `packages/connectors/src/drivers`.  Data Sources administrators manage it through `/api/source-drivers`.  Installation accepts only pinned artifacts, verifies integrity before extraction, rejects unsafe archive entries, and never executes package scripts.  License acceptance is an audit event containing the exact text’s SHA-256 hash.  No schema migration is needed for these events.

The install routes check the session, its CSRF token, and the Data Sources role as each request arrives, before any of its body is read, and keep the app's normal body limit.  An offline install uploads each archive in its own request, streamed to disk with its hash checked and its 96 MiB limit enforced as the bytes arrive.  Downloads stream the same way, after a check that the drivers folder has room for the catalog's unpacked size.

Versioned folders and an atomic active manifest live on persistent storage.  Once a new version is active, the one it replaced is removed, and at start the server removes whatever an install left when it stopped part way.  A filesystem lock serializes changes across processes sharing that storage.  It records the host, process, and time that took it, and is taken over once that process is gone, or after an hour, longer than any install can run, when it can't be checked.

An installed driver runs with the server's file access, so it can read `/config` and anything else the server's account can.  That is why only the catalog's vendor drivers, at pinned hashes, can be installed.  Driver sessions run in separate processes so a blocking native call can be terminated when its deadline or abort signal fires.  Each process starts from an allowlisted environment with no `RIOSOMA_` settings, and whatever it says is stripped of the source's secrets and every secret the server holds.  Each new call checks the active installation, so removing a driver stops subsequent source reads.

IBM's driver loads IBM's client from beside it: the driver's process gets `IBM_DB_HOME` and the library path (`LD_LIBRARY_PATH`, or `DYLD_LIBRARY_PATH` on macOS, where IBM's add-on names its library by the path it was built at) pointing at the installed client, and never one from the server's own settings.  The add-on is taken from the package's `build.zip` for the platform, as the package's own installer does, with its SHA-256 checked, and links in IBM's archive become copies of the file they name.  IBM's connection string can't escape a semicolon, so values are sent as written and one with a semicolon is refused before the driver starts (`sources.test.ibmSemicolon`).  Informix connections turn on `DELIMIDENT`, since every name the connector sends is double-quoted, and a table's BOOLEAN columns, which DRDA describes as SMALLINT, are found in `syscolumns`.  IBM's add-on queues its native work on the thread pool without waking the event loop on some Node builds, so the driver's process keeps a 10 ms timer running while a call is under way.

The live suite, `src/drivers/installed.live.test.ts`, runs each system against a real database through a driver installed in `RIOSOMA_DRIVERS_DIR`, installed the way the server installs one.  It creates a `rio_test_items` table and a `rio_test_view` view with its own connection, runs the source's test, listing, keys, describe, preview, batched reads with exact keys, a query, and an abort, and drops both afterward.  Each system runs only when its settings are set: `RIOSOMA_TERADATA_HOST`, `RIOSOMA_TERADATA_USER`, and `RIOSOMA_TERADATA_PASSWORD` (with `RIOSOMA_TERADATA_PORT` and `RIOSOMA_TERADATA_TLS` optional), `RIOSOMA_DB2_HOST`, `RIOSOMA_DB2_DATABASE`, `RIOSOMA_DB2_USER`, and `RIOSOMA_DB2_PASSWORD` (with `RIOSOMA_DB2_PORT` optional), and the same four for `RIOSOMA_INFORMIX_` (its port is the DRDA port, 9089 by default).  Run `pnpm --filter @riosoma/connectors exec vitest run src/drivers/installed.live.test.ts` directly so the test process receives those settings.  It never installs or downloads a driver itself.

## Synced tables

- **Settings** live in `rio_app.table_sources`: the source, what to read, the key columns, minutes between syncs (or manual only), whether overrides are allowed, the removal hold threshold, whether records whose rows leave the source are removed (unset means yes, except for feeds), the sync status, and a feed's last validators.
- **Physical storage** adds four system columns to the table's record table: `__source_key` (text, unique among live rows), `__overrides` (JSON, null when the row has none), `__synced_at`, and `__source_gone` (true for rows the source no longer has).
- **The key** is the source values of the key columns, written as a JSON array in a canonical form.  It's how a record keeps its ID, its own fields, and its overrides from one sync to the next.  Key candidates come from the source's primary key and unique constraints, and the person creating the table confirms them.
- **Creating** one is a `table.create` command with `source` settings and fields carrying `source.column`.  The table starts empty and its first sync is queued at once.
- People **can't create or delete records** in a synced table, **can't change a source field's type**, and can change source values only by overriding them.  Renaming fields, hiding them, formatting them, and adding local fields all work as usual.

## Syncing

A sync runs in two phases so edits aren't blocked while a slow source streams rows:

1. **Stage** (no locks held): read the source in batches and load each batch into a temporary staging table through `jsonb_to_recordset`, keyed by `__source_key`.  Rows with an empty key or a duplicate key fail the sync with a message naming the key.  Each staged row keeps its place in the source's order, so records the sync adds appear in that order.
2. **Apply** (under the database's command lock, in one transaction), comparing staging with the table in SQL:
   - **Added**: keys the table doesn't have get new records.
   - **Returned**: keys marked gone come back with their original IDs, own fields, and overrides.
   - **Changed**: source fields whose value differs.  An overridden cell keeps its override, and its stored source value updates.  When the new source value equals the override, the override clears itself.
   - **Removed**: live keys missing from staging are marked `__source_gone` and hidden from every read.  The purge removes them after the trash retention period.  A table that keeps missing rows (`removeMissing: false`, a feed's default) skips this step and the hold.
   - **Hold**: when the removals would exceed the table's hold threshold (half the records by default, and only for tables of 20 records or more), nothing is applied.  The table's status becomes `held` with the counts, and someone confirms with `table.sync` and `confirmRemovals`, or fixes the source.

The apply writes one `table.synced` change carrying the updated table and the counts, never values, and one audit event.  Clients reload the table's rows when it arrives.  Syncs belong to no one's undo history.

**Scheduling**: each replica checks every 30 seconds for due tables and claims them with `FOR UPDATE SKIP LOCKED` and a lease, so one sync runs per table across replicas, at most two at a time per replica.  A failure records its message key and retries with backoff (5 minutes, doubling, never later than the table's own interval).  `table.sync` queues one now.

## Incoming webhooks

A webhook source's tables aren't synced: posts fill them as they arrive.

- **The address** is `/api/inbound/<token>`, with a 256-bit token made when the source is saved and shown in that answer only.  `rio_app.source_hooks` keeps its SHA-256 hash, and `POST /api/sources/:id/webhook-address` replaces it, so the old one finds nothing.  The logger redacts the token from every path.
- **Checks**, in order: the token, pausing (`503`), the pace (a one-minute window per source, `postsPerMinute`, counted in the row so replicas share it, `429` with `Retry-After`), and the content type (`415`), all in an `onRequest` hook before any of the body is read, so a post too large still counts against the pace.  Then the body limit of 1 MB (`413`, Fastify's own limit, logged by the route's error handler), the signature, the JSON, and where the records are.  Every refusal answers with a plain code, `{"error": "signature_invalid"}`.  Signatures are HMAC-SHA256 with the sealed `signingSecret`, either `t=…,v1=…` over `<t>.<body>` (Riosoma's own outgoing form) or hex over the body, optionally with a time header covering `<time>.<body>`.  The digest is checked first and the time second, so a validly signed post outside the tolerance is refused as a replay.
- **Queueing**: an accepted post is logged, its body goes to `source_hook_posts` as the text that arrived (not jsonb, which would round whole numbers past 2^53) with the records path and split it was accepted with, and the answer is `202` with the count and the delivery's ID.  The writer reads it with the same `parseJson` the address used, so long whole numbers stay exact as values and as keys.  `InboundWriter` writes posts one at a time, a source's in order, each in one transaction: for every table that syncs from the source, it runs `record.create` and `record.update` through the command bus as the table's creator, marked with `actor.source`, inside a savepoint, so a post is written whole or refused for that table.  `applyRecords` lets such an actor add records to that source's synced tables, and its updates keep people's overrides, updating the source value behind them the way a sync does.  Keys are the key paths' values as their exact text, stored in `__source_key`, and a later record with the same key in one post stands for it.  Values convert by the file sources' rules, and a value a field refuses arrives empty.  Choices are added as a sync adds them, but only up to `LIMITS.choicesPerField` and names up to `LIMITS.nameLength`, since anyone with the address can post, and a record naming one past that is refused while the rest are written, with `sources.webhook.choicesFull` on the delivery.
- **Retries**: a lock timeout, deadlock, serialization failure, statement timeout, or connection error (`transientFailure`) rolls back the post's whole transaction, every table's part with it, and the post stays queued with `attempts`, `first_failed_at`, and `next_attempt_at`, waiting 30 seconds and doubling to 15 minutes.  Its delivery shows `sources.webhook.retrying`, and later posts from the source wait behind it.  After 10 tries over at least an hour, `failed_at` is set, the delivery shows `sources.webhook.gaveUp`, the post is kept, it holds up no later post, and the source's creator gets one `webhookFailed` notification.  A refusal that would happen again (a rejected command, a missing table person, an empty key, or an unexpected error inside one table's write) ends the post for that table, as before.
- **The log** (`source_hook_deliveries`) keeps each source's last 100 posts, never pruning one still held, waiting or failed, and shows those too: time, status, refusal code, size, record count, the write's error, and the body only while `bodies_until`, set for an hour by `PUT /api/sources/:id/webhook-bodies`, is ahead of the server's clock.  Once it passes, the writer's tick (`pruneHooks`) and any read of the log forget the bodies kept, and starting a new hour after the last one ended forgets them first.
- **Mapping**: the connector's preview opens a two-minute window (`samples_until`) that each preview extends.  Posts that arrive inside it are kept in `source_hook_samples` as the text that arrived, the last 10, read again with `parseJson` and the source's current settings, and the writer's tick forgets them once the window closes, so the wizard's field step shows only posts sent while it's open.  A synced table's source columns are JSON paths, taken without a sample, and its key is optional.
- **Restoring** an archive with a webhook's table passes the source's kind to `initialStatus`, so the table comes back idle with no sync due, like a new one.

## Overrides

- Stored in `__overrides` as `{ fieldId: { source, by, at } }`, while the field's own column holds the value everyone sees.  Filters, sorts, formulas, lookups, and the API all read the column, so overrides need no special handling anywhere else.
- **Setting** one is an ordinary `record.update` on a source field, allowed when the table allows overrides and the person can edit records.  Setting a value equal to the source's clears the override instead.
- **Clearing** is `record.clearOverrides`, which puts the source's values back.
- Both are ordinary record changes: they're undoable, audited, broadcast, and in the record's history, with the override state in the change.
- Reads include `overrides` on each record, so the grid can mark overridden cells and show the source's value.

## Live tables

A synced table from PostgreSQL, MySQL, or SQL Server can read its source live instead of copying it (`freshness: 'live'` in its settings).  The server's `sources/live.ts` reads, `sources/live-commands.ts` checks commands, and `packages/connectors/src/live/` translates and pools.

- **Two-phase paging, from the source.**  The order is the keys of every row the view's filter and the reader's record rules admit, in the view's sort order and then by key, kept per replica as a snapshot (`LiveReads`), shared for 30 seconds and kept for 15 minutes for the reader paging it.  A page reads its rows by key.  A view lists at most 250,000 keys (`RIOSOMA_LIVE_MAX_KEYS`) and says when it cut the list short.
- **Translation.**  Filters and sorts compile to the source's dialect only where the answer is exactly Riosoma's: text, number, checkbox, date, and single-choice source fields over columns that compare the way Riosoma does.  Case-insensitive text compares lowercased bytes, choice labels compare byte for byte, and a day in a time zone becomes the span of instants it covers.  Anything else (a local field, a source field some record overrides, a multiple choice) is left out: from an `and` group alone, or with its whole `or` group, so the view only ever widens.  The page's `live` note names what was left out.  Text sorts use the source's collation, and the note says so.
- **Record rules** translate strictly, as `AccessScope` reads them: a condition that can't translate matches nothing.  A live table refuses a rule on anything but source fields no record overrides, and refuses an override of a field its rules read, so rules there are always exact.  Elsewhere, a person a rule limits sees only the records a live read confirmed in the same request (`AccessScope.confirmLive`).
- **Identity.**  Each key a page shows gets a record here (`identify`), holding its ID, overrides, and local fields, so comments, history, commands, and undo work unchanged.  Before a command changes source fields, the server reads their current source values outside the transaction and writes them into the record, so overrides and history record what the source says.
- **Safety.**  Each source gets a pool of at most three sessions, closed after a minute idle and replaced when the source's settings change.  Every read runs in a read-only transaction where the system has one (not SQL Server), with a statement timeout (15 seconds, `RIOSOMA_LIVE_TIMEOUT_MS`), and values travel as parameters, or as Unicode literals for SQL Server.  Failures map to `sources.live.*` keys, or the sync's keys for a missing table or column, and the grid shows them in place of rows.
- **Switching** to Live keeps every record's overrides and local fields and stops syncs.  Switching to Copy queues a first sync, sets `switchingToCopy`, and reads live until that sync's apply, which clears it.
- Paths that need every record (links, lookups, rollups, counts, formulas, kanban and calendar reads, summaries, dashboards, find in view, duplicates, joins, the API, and shared views) refuse a live table.

## Join discovery

- **Suggestions** (`POST /api/databases/:databaseId/join-suggestions`, for people who can change fields) profile the database's text, number, email, URL, phone, auto number, and record ID fields in a read-only transaction and score pairs by coverage (how many values find a match), uniqueness (how many values on the other side are distinct), and whether the names point at each other.  Tables over 10,000 records are sampled, and the request answers with what it found within its time budget.
- **Links by matching values** are link fields with `match` set to a field on each side.  Records link wherever the values are equal (numbers as plain decimal text, text trimmed and case-sensitive, empty values never), and people can't edit those cells by hand.  Both sides of the link carry the mirrored `match`.
- **Upkeep:** turning matching on, converting a field, and restoring a table rebuild the whole junction.  Record edits, new records, undo, and syncs refresh only the records they changed, in the same transaction.  Hash indexes on both matched fields keep lookups fast, and they're dropped when no link follows the field anymore.
- Trashing a matched field turns its link back into an ordinary one and keeps the links it had.  Undoing that matches it again.
