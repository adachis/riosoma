# Security walkthrough

This is a threat model of the checked-in application, not a certification of a deployment.  The server code is authoritative when this walkthrough and an implementation differ.  [Field and record permissions](permissions.md) describes the access model, its read and write paths, public sharing, background actors, realtime redaction, and unit administration.  Those rules are referenced here rather than repeated.

## Assets and attackers

| Asset                                                             | Where it crosses a boundary                                                                                      |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Organization data, schemas, comments, history, and exports        | Browser requests, API calls, realtime messages, PostgreSQL, background jobs, and outbound destinations           |
| Credentials in the vault, wrapping keys, and vault authentication | Server configuration, credential adapters, encrypted database values or external references, and connector calls |
| Files, previews, imports, and archives                            | Uploads, remote downloads, storage, parsers, scanners, and authorized downloads                                  |
| Sessions, reset links, and second factors                         | Browser cookies, authentication routes, session storage, and account administration                              |
| Personal and application API tokens                               | Bearer headers, token hashes, consent grants, database restrictions, and revocation                              |
| Audit history and release metadata                                | Audit storage, administrative exports, the hub, and signed update feeds                                          |

An anonymous internet attacker can send requests to public endpoints and submit public forms.  A signed-in member can substitute resource IDs, submit commands, upload files, and try to use privileges the server has but the member lacks.  An organization administrator can change the settings their administrative role and unit scope allow, including destinations and sharing policy.  Administrative authority is therefore part of the threat model, not proof that a supplied address or file is safe.

A malicious data source controls responses, redirects, DNS answers, records, and attachments.  A malicious import file controls compressed sizes, container members, document structures, and text that later appears in a page or message.  A compromised dependency executes within the process that loads it, potentially including native driver or parser code.  Network guards, parser limits, and package checks address parts of these threats, but do not turn the server process into an isolation boundary against its own dependencies.

It exercises mixed DNS answers, connection pinning, redirects, and the explicit private-network opt-in.
- [`data/tenant.corpus.test.ts`](../../apps/server/src/data/tenant.corpus.test.ts) consumes `corpora/tenant.ts` for cross-organization resource substitution through session routes, token routes, commands, and tool calls.  It also checks route inventory coverage and sentinel leakage.
- [`data/imports/zip.corpus.test.ts`](../../apps/server/src/data/imports/zip.corpus.test.ts) consumes `corpora/zip.ts` across workbook, library, organization archive, and driver archive readers, including actual expansion larger than declared sizes.
- [`sites/render.corpus.test.ts`](../../apps/server/src/sites/render.corpus.test.ts) and [`apps/e2e/tests/x-security-corpora.spec.ts`](../../apps/e2e/tests/x-security-corpora.spec.ts) consume `corpora/xss.ts` for rendered sites, email, rich text, and browser execution checks.
- `corpora/demo.ts` records explicit route and command decisions.  [`demo/regressions.test.ts`](../../apps/server/src/demo/regressions.test.ts) and [`demo/visibility.test.ts`](../../apps/server/src/demo/visibility.test.ts) exercise the demo boundary and its public response behavior.

## Browser to server

[`apps/server/src/http/policy.ts`](../../apps/server/src/http/policy.ts) requires declared policies for `/api/` and `/v0/` routes and rejects undeclared API policies at startup.  Public, setup, session, token, and administrative policies select the authentication path.  Administrative policies declare an area and scope.  They do not replace resource-level checks inside handlers.  Unsafe session and administrative requests must echo the session's `x-csrf-token`.  Routes with `beforeBody` perform their admission checks before reading their large or streamed body.

[`auth/passwords.ts`](../../apps/server/src/auth/passwords.ts) hashes passwords with Argon2id and runs a dummy verification for missing password hashes.  [`auth/sessions.ts`](../../apps/server/src/auth/sessions.ts) creates random session tokens, stores their SHA-256 hashes, and checks expiry, revocation, and active identity when resolving them.  Cookies are HttpOnly, SameSite=Lax, and Secure when the request protocol is HTTPS. Session resolution also applies effective unit policy.  [`auth/account-security.test.ts`](../../apps/server/src/auth/account-security.test.ts) covers reset-token lifecycle, session termination, concurrent account changes, and protected reads after revocation.  [`auth/mfa/`](../../apps/server/src/auth/mfa/) and [`auth/sso/`](../../apps/server/src/auth/sso/) contain the additional authentication flows and their tests.  This does not imply every installation requires those flows.

[`auth/tokens.ts`](../../apps/server/src/auth/tokens.ts) verifies token secret hashes with a timing-safe comparison, checks expiry and revocation, requires the route's token scope, and carries the token's database restriction into the actor.  Guests cannot create these tokens.  [`authorization/store.ts`](../../apps/server/src/authorization/store.ts) supplies application-token authentication.  The OAuth grant and database-access semantics are documented in [permissions.md](permissions.md#oauth-app-grants).

[`app.ts`](../../apps/server/src/app.ts) installs Helmet and a CSP with same-origin script and style sources, no objects, no base URI, same-origin form actions, and same-origin frame ancestors.  Google Picker, maps, and signed file-store origins add sources only through their configuration paths.  Worker and image directives permit specific `blob:` or `data:` uses.  [`http/shell.ts`](../../apps/server/src/http/shell.ts) additionally authorizes the shell's startup recovery script by its content hash.  HSTS is enabled in production.  The error handler emits application error bodies and generic internal errors rather than sending raw exceptions.  Fastify's JSON parser rejects prototype-poisoning keys, and the default request body limit is 10 MiB. Individual upload routes have their own limits.

Rate limits are local to particular surfaces.  [`auth/attempts.ts`](../../apps/server/src/auth/attempts.ts) records hashed attempt keys in PostgreSQL with account and IP windows.  [`data/public-forms.ts`](../../apps/server/src/data/public-forms.ts) limits submissions.  [`data/shared-view-routes.ts`](../../apps/server/src/data/shared-view-routes.ts) uses in-memory password-attempt limiters.  [`sites/routes.ts`](../../apps/server/src/sites/routes.ts) limits site requests and submissions.  [`mcp/rate-limit.ts`](../../apps/server/src/mcp/rate-limit.ts) implements configured tool-request quotas and audit events.  These are not a single global HTTP quota.

## Server to databases and tenant resources

[`data/access.ts`](../../apps/server/src/data/access.ts) resolves resource roles and grants using the actor's organization and active membership.  Resource queries include organization identity, and missing or foreign resources are refused through the access layer.  [`data/permissions/enforce.ts`](../../apps/server/src/data/permissions/enforce.ts), [`data/commands/index.ts`](../../apps/server/src/data/commands/index.ts), and [`data/physical/`](../../apps/server/src/data/physical/) enforce field and record restrictions on writes and reads as described in [permissions.md](permissions.md#enforcement-in-sql-from-one-place).  Tenant isolation here depends on application queries and access checks.  The tenant corpus is the regression evidence for those paths, not evidence that every possible future query is safe.

[`packages/db/src/sql.ts`](../../packages/db/src/sql.ts) separates SQL values and quoted identifiers.  [`packages/db/src/connection.ts`](../../packages/db/src/connection.ts) implements the chosen PostgreSQL TLS mode, including modes with weaker verification.  [`packages/db/src/transport.ts`](../../packages/db/src/transport.ts) allows plaintext fallback in `prefer` mode only after the server explicitly refuses TLS. The local test kit deliberately uses a private disposable database, not deployment credentials.

[`auth/database.ts`](../../apps/server/src/auth/database.ts) writes audit events with organization, actor, action, metadata, and unit context where supplied.  [`data/organization-admin/routes.ts`](../../apps/server/src/data/organization-admin/routes.ts) protects audit reads and exports with the audit administrative role.  [`data/organization-admin/store.ts`](../../apps/server/src/data/organization-admin/store.ts) scopes reads and checks the stored event hash chain, including retained markers for purged entries.  This detects inconsistencies in that stored chain.  It does not provide an independently trusted copy against a database administrator who can rewrite the database and its functions.

## Server to credential storage

[`credentials/service.ts`](../../apps/server/src/credentials/service.ts) selects database or external vault storage and binds stored credentials to organization, owner context, and purpose.  [`credentials/envelope.ts`](../../apps/server/src/credentials/envelope.ts) uses per-value random data keys and AES-256-GCM with associated data, wraps each key, and clears the temporary data-key buffer.  External storage keeps an authenticated reference locally.  Vault failures produce an unavailable error rather than silently falling back to another store.  [`credentials/service.test.ts`](../../apps/server/src/credentials/service.test.ts) and [`credentials/envelope.test.ts`](../../apps/server/src/credentials/envelope.test.ts) cover reference isolation, binding, failure behavior, and encryption integrity.

[`secrets.ts`](../../apps/server/src/secrets.ts) seals instance-local values with owner and purpose context.  [`config.ts`](../../apps/server/src/config.ts) loads or generates the instance key and stores configuration under the configuration directory.  [`logger.ts`](../../apps/server/src/logger.ts) redacts known secret keys, authorization and cookie headers, URL userinfo, and known secret-bearing paths, and logs request paths without query strings.  These mechanisms do not encrypt process memory, nor guarantee that arbitrary new log fields are safe.

## Server to connector service and external sources

[`sources/connector-service.ts`](../../apps/server/src/sources/connector-service.ts) starts a local connector child on loopback with a random bearer token, or obtains a configured service endpoint and shared token.  Its stored token file is created with mode `0600` under a directory created with mode `0700`.  [`apps/connector-service/src/token.ts`](../../apps/connector-service/src/token.ts) requires tokens of at least 32 characters and compares their digests with a timing-safe comparison.  File-backed tokens refresh at most once per second.

[`apps/connector-service/src/app.ts`](../../apps/connector-service/src/app.ts) admits service API calls only with that token, before reading their bodies.  Health and readiness probes are public.  Calls carry source settings, credentials, and the server's network policy.  The service validates the wire shape, redacts supplied secrets from connector errors, avoids logging bodies, and bounds request bodies.  The token authorizes the server as a whole.  It does not identify an end user or independently authorize an organization.  The service trusts the authenticated server to supply the appropriate settings and network policy.  The local link uses HTTP, so a separately deployed link also needs transport protection appropriate to its network.

[`sources/hosts.ts`](../../apps/server/src/sources/hosts.ts) delegates private-host decisions to [`packages/connectors/src/network/private.ts`](../../packages/connectors/src/network/private.ts).  [`data/imports/download.ts`](../../apps/server/src/data/imports/download.ts), [`automations/outbound.ts`](../../apps/server/src/automations/outbound.ts), [`webhooks/url.ts`](../../apps/server/src/webhooks/url.ts), and [`mcp-client/fetch.ts`](../../apps/server/src/mcp-client/fetch.ts) check destinations and resolved addresses.  The shared SSRF tests cited above demonstrate the different redirect behaviors and address pinning.  In production, private destinations are refused unless the operator enables `RIOSOMA_AUTOMATIONS_ALLOW_PRIVATE_HOSTS`.  This switch deliberately widens the reachable network.  These checks do not authenticate the contents returned by an allowed source.

## Files and imports to storage and workers

[`data/files/routes.ts`](../../apps/server/src/data/files/routes.ts) checks access through visible attachment fields and records, or ownership of an unattached upload.  Downloads carry an appropriate disposition, `nosniff`, and a sandboxed CSP. Signed downloads delegate serving to the selected storage provider after the server's checks.  [`data/files/safety.ts`](../../apps/server/src/data/files/safety.ts) inspects types and active content and bounds archive expansion, member count, and nesting.  Its result distinguishes held content from allowed content with notes.  It is not a universal malware detector.  [`data/files/safety.test.ts`](../../apps/server/src/data/files/safety.test.ts) specifies which cases are held and which are only noted.

[`data/files/scanning.ts`](../../apps/server/src/data/files/scanning.ts) runs the optional ClamAV queue, keeps unavailable scans quarantined, deletes detected infected bytes, and records scan outcomes.  [`data/files/settings.ts`](../../apps/server/src/data/files/settings.ts) restricts scanner endpoints to operator-approved addresses.  [`data/files/metadata.ts`](../../apps/server/src/data/files/metadata.ts) withholds ordinary URLs for quarantined files.  Oversized files are blocked by default, but explicit policy can permit downloads labeled as unscanned.  [`data/files/scanning.test.ts`](../../apps/server/src/data/files/scanning.test.ts) covers quarantine, unavailable scanners, infected-byte deletion, and oversized policy.  Scanning is conditional on configuration or saved organization settings.

[`data/imports/zip.ts`](../../apps/server/src/data/imports/zip.ts) bounds directory entries and extraction output.  The archive corpus cited above tests multiple consumers, not just upload sniffing.  [`ingest/extract/limited-worker.ts`](../../apps/server/src/ingest/extract/limited-worker.ts) forks parser hosts without inherited environment variables, applies a parent-owned deadline, and kills the host when finished.  [`ingest/extract/limited-worker-host.ts`](../../apps/server/src/ingest/extract/limited-worker-host.ts) bounds worker memory and samples resident growth, including native allocations.  These processes still run as the application's operating-system user.

[`scripts/sandbox.ts`](../../apps/server/src/scripts/sandbox.ts) and [`scripts/sandbox-worker.ts`](../../apps/server/src/scripts/sandbox-worker.ts) run user scripts through a QuickJS runtime in a worker with resource limits, a parent deadline, and an explicit host-call interface.  Background business jobs have a different trust relationship.  [`automations/run.ts`](../../apps/server/src/automations/run.ts), [`ai-fields/worker.ts`](../../apps/server/src/ai-fields/worker.ts), [`reports/worker.ts`](../../apps/server/src/reports/worker.ts), and [`signatures/worker.ts`](../../apps/server/src/signatures/worker.ts) resolve their responsible person's access.  Their detailed authority and exceptions are in [permissions.md](permissions.md#everything-else-that-reads).  A queue entry is not itself an authorization grant.

## Server to realtime clients and the hub

[`realtime/routes.ts`](../../apps/server/src/realtime/routes.ts) validates WebSocket origin, requires a session and a CSRF-bearing hello, limits frame size and message queues, rechecks sessions, and closes idle or revoked connections.  [`realtime/hub.ts`](../../apps/server/src/realtime/hub.ts) and [`realtime/redact.ts`](../../apps/server/src/realtime/redact.ts) apply per-connection access and redact changes as described in [permissions.md](permissions.md#realtime-filtered-per-connection).  A database notification is not sent verbatim to every browser.

The external hub is a separate service from the in-process realtime hub.  [`feedback/hub.ts`](../../apps/server/src/feedback/hub.ts) sends bounded, redacted feedback text and context without a screenshot or sender field, and validates returned issue URLs.  [`telemetry/service.ts`](../../apps/server/src/telemetry/service.ts) sends usage counts only after the owner enables them and honors the operator's off switch.  [`updates/feed.ts`](../../apps/server/src/updates/feed.ts) verifies feed signatures with configured Ed25519 keys and rejects stale or future-dated feeds outside its permitted windows.  A signed feed authenticates feed bytes, not the safety of all code in the release.

[`apps/hub/src/index.ts`](../../apps/hub/src/index.ts) bounds incoming bodies, validates contracts, rate-limits anonymous writes by network address, and checks a bearer token for protected statistics.  Installation IDs are caller-chosen.  The hub treats relayed report text as fenced text when publishing it.  Local dynamic scans do not exercise the hosted hub or any live provider.

## Dependency and dynamic checks

The nightly workflow's existing `security` job runs the advisory scripts in `tools/ci/`, and its `image` job scans built images for fixable high and critical vulnerabilities.  Lockfiles and the install-time policy in `pnpm-workspace.yaml` constrain dependency installation.  These checks find known issues and policy violations, not every malicious package.

The `zap` job in [`.github/workflows/nightly.yml`](../../.github/workflows/nightly.yml) invokes [`apps/e2e/zap.ts`](../../apps/e2e/zap.ts).  It builds the browser-test web artifact and uses the existing `startStack` helper with a fresh PostgreSQL database and the built server.  It completes first-run setup, disables update checks, telemetry, and hub submissions for this fixture, and scans the public surface without handing credentials to the scanner.  The baseline spider and active API scan use a digest-pinned container and the server's `/api/v1/openapi.json`.  Both HTML and JSON reports are retained.  Scanner errors, absent reports, malformed alert inventories, and unaccepted high-risk alerts fail the job through [`zap-report.ts`](../../apps/e2e/zap-report.ts).

Accepted findings belong in [`.github/zap/rules.json`](../../.github/zap/rules.json) as numeric rule IDs mapped to one-line review reasons.  They are classified as informational in scan configuration but remain in the reports.  An empty object means no findings are accepted.  Changing this file changes the gate, so a reason must explain the particular exposure being accepted.  Lower-risk findings remain reportable even though they do not fail the high-risk gate.  Rule 100001 is accepted for HTML responses to the API scanner's probes of the root, bare `/api`, and random non-API paths, where `app.ts` intentionally serves the application shell.  The local scan also identified duplicate configured WebSocket CSP sources, which are now deduplicated.

## Known gaps and closure criteria

| Gap or limitation                                                                                                                                                         | What would close it                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public-surface scans do not authenticate, seed accessible records, or exercise the complete private API, public-sharing configurations, realtime flows, or live providers | Add isolated authenticated scan contexts and representative resources and sharing fixtures, retaining the targeted permission and corpus tests                               |
| HTTP is supported, Secure cookies depend on the request protocol, and some database TLS modes weaken verification                                                         | Require HTTPS at the deployment edge, configure trusted proxies narrowly, and choose certificate and hostname verification for database connections                          |
| Connector bearer tokens authorize the whole server, and the configured link can use HTTP                                                                                  | Protect the service network and token distribution, use verified encrypted transport across hosts, and add narrower service identities if independent callers are introduced |
| Private-network opt-in deliberately bypasses the default SSRF destination restriction                                                                                     | Keep it off for untrusted destinations, or enforce a narrower destination allowlist and network egress policy outside the process                                            |
| Antivirus scanning can be disabled, and explicit oversized-file policy can allow unscanned downloads                                                                      | Provision and monitor an approved scanner, enable scanning, and retain the blocking oversized policy                                                                         |
| Parser processes, connector drivers, and server dependencies share the application's operating-system identity                                                            | Isolate risky native code with separate identities, filesystem restrictions, and network restrictions appropriate to the deployment                                          |
| Endpoint-specific and in-memory limiters do not establish a global, shared request budget                                                                                 | Add measured shared quotas and edge limits for the exposed routes and deployment topology                                                                                    |
| Stored audit-chain verification cannot establish integrity against a privileged database rewrite                                                                          | Export audit events or authenticated checkpoints to an independently controlled append-only destination                                                                      |
| Dependency advisory and image checks cannot prove that an unknown dependency or signed release is trustworthy                                                             | Add independently reviewed provenance and integrity verification and restrict the runtime privileges of installed code                                                       |
