# Rio

How the assistant works: where it runs, what it may touch, and how its changes stay undoable.  Shapes live in `packages/contracts/src/rio.ts`, and providers and models in `packages/ai`.

## Principles

- **Rio acts as the person.**  Every read goes through `AccessScope` and every change through the command bus as the person asking, so Rio can never see or do more than they can, and everything it does is audited, broadcast, and in their undo history.
- **Off until an admin turns it on.**  An admin with the AI role chooses which providers people's data may go to, stores their keys (sealed like source secrets, or set in the server's environment), and picks an everyday model and a power model.  Local models on the organization's own hardware are marked as such, since data never leaves.
- **Preview big, apply small.**  With the default autonomy, changes to up to 20 records with no deletes apply at once, followed by a receipt with Undo.  Anything bigger, and every delete, arrives as a plan the person applies.  People can choose to be asked every time.  Admins set the ceiling.
- **Honest about cost.**  Each reply records its tokens and, when the model's price is known, its cost.  An organization can set a monthly budget, and Rio pauses at it.  Energy and carbon estimates join the usage line when the estimation package lands.

## A conversation

1. The person asks in the Rio panel.  The request carries the text, the tier, their autonomy, their language, and where they are (database, table, view, record, and selection).
2. The server builds the model's input: a short system prompt with Rio's voice and rules, the conversation so far (trimmed to fit), and the context resolved into names and schemas the person can see.
3. The model streams.  Text streams to the browser as it arrives.  Tool calls run on the server, one at a time, each announced with a "working" event so the panel can say what Rio is doing.  The loop ends when the model stops calling tools, or after 8 rounds.
4. The reply is stored with its blocks and usage.

Replies stream as server-sent events over a plain `POST`, so they work behind the same proxies as the rest of the app.  Closing the panel or pressing Stop aborts the model call.

## Tools

| Tool | Does |
|---|---|
| `list_databases` | The databases the person can open |
| `get_schema` | Tables and fields first, followed by compact lists of views, dashboards, interfaces, and automations |
| `get_dashboard` | One dashboard's visible tiles |
| `get_interface` | One interface's visible pages and blocks, without executable code |
| `get_automation` | One automation's trigger, step kinds, and visible field references, without destinations, payloads, or scripts |
| `find_records` | Records matching a filter and sorts, at most 50, with chosen fields |
| `count_records` | How many records match a filter |
| `propose_changes` | Commands for records, fields, tables, views, dashboards, interfaces, and automation drafts, with a summary and steps |
| `ask_question` | A question with suggested answers, when Rio needs a choice |

`propose_changes` validates every command against the contracts, fills in the IDs the model left out, and checks permissions without applying anything.  Then autonomy decides: apply now and return a receipt, or return a plan block.  Applying a plan later runs its stored commands through the bus in one undo group, refusing if the database changed in ways that break them, and marks the plan applied or failed.

Tool results sent back to the model carry only what the person can see, trimmed to a budget, and never secrets.  Text in records is data, never instructions: the system prompt says so, and tool results are wrapped so the model can tell them apart.

## Storage

`rio_app.rio_conversations`, `rio_app.rio_messages` (blocks and usage as JSON), and `rio_app.rio_plans` (the filled-in commands, status, and the undo group once applied), all scoped to their organization and person.  People see only their own conversations.  Deleting a conversation deletes its messages and pending plans.

## The panel

The AI button in the top bar opens a panel on the right, where the Rio pet sits above the composer.  Rio's mood follows the conversation: thinking while it works, talking while text streams, happy when changes apply, and curious when it asks a question.  Plans show their steps with Apply and Dismiss, receipts show Undo, question blocks show tappable answers, attention blocks pin above the composer, and each reply ends with a quiet usage line.  Everything is keyboard reachable, and the panel works at phone width as a full-screen sheet.

## AI fields

An AI field is an ordinary field of one of seven types (text, long text, single or multiple select, number, checkbox, or date) with `ai` settings: a prompt that names the record's fields in braces, stored with field IDs, a tier (`fast` takes the everyday model, or the power model when that's all there is, and `careful` the power model), and a trigger.  `apps/server/src/ai-fields/` holds the rest.

- **Queueing.**  `recordChange` calls `queueAiFieldRuns`, which queues a row in `ai_field_runs` when a change touches a field the prompt reads, directly or through a formula, lookup, rollup, or count of the record's own fields.  A change to a linked record queues runs too, when a lookup, rollup, count, or link in the prompt reads what changed: the queue follows the links back through their junction tables, up to four links and 1,000 records a change.  Formulas need no such step, since they're computed as they're read.  At most one run per cell waits, so a burst of edits asks once.  The cell and field menus queue runs on request, and a bulk run over all or empty records groups its runs in `ai_field_jobs`, which the field's header follows and which can be canceled.  Runs of more than 25 records need the estimate confirmed first.
- **Loops.**  `readsBack`, the check that keeps formulas from reading themselves through other tables, follows AI prompts too.  Saving an AI field's settings, or a formula, lookup, rollup, conversion, or primary field that would read an AI field whose prompt reads it back, is refused (`aiFields.prompt.circular` or `aiFields.loop`).  Before each run the worker checks again and fails a run whose prompt reads its own value back (`aiFields.run.loop`) without asking or writing anything.  A run's own write never queues its cell again, and its `depth` counts toward the automation depth limit alongside automations, so an AI field and an automation that set each other off stop after five steps.
- **Running.**  Claims go one at a time across every server, under an advisory lock, which is how no organization has more than four runs going at once.  Each claim reads the organizations with open runs one index step at a time and takes the oldest few of each, so every organization with work waiting gets a turn before any gets a second, and one organization's bulk run never holds up another's.  Each claimed run holds a lease, which another server takes over once it runs out, as after a crash or a shutdown that stopped a call midway.  A rate limit, or a provider briefly down, sends a run back to wait longer each time, up to four more tries, and a spent monthly budget sends it back until the month turns, or until an admin changes the AI settings.  The answer is read strictly as the field's type, and a select answer outside the options is the cell's error, with the answer kept in `message_params` to show, never a new option.  The value goes through the command bus as the field's person, marked with the field and run in the audit log, so history, undo, realtime, and automations see it.
- **Usage.**  Each run keeps its model, tokens, cost, and outcome, and its cost joins `ai_spend`, so the admin page's spend and the monthly budget count it.  Finished runs are deleted after 30 days, and their cost stays in the month's spend.  A table's status reads only live runs, the waiting and failed ones, through an index that holds nothing else.  The organization's `aiFields` setting stops new runs and keeps the values already written.
- **Writes from outside.**  The REST API and MCP refuse writes to an AI field, as they do a formula's, unless the request sets `overrideAiFields`.

## Routines

A routine is a recurring job a person describes in plain words, which Rio carries out on a schedule in one database, as that person.  Shapes live in `packages/contracts/src/routines.ts`, and the rest in `apps/server/src/routines/`.  Migration `0059_routines` adds `rio_routines`, `rio_routine_runs`, and `rio_routine_approvals`, and three notification kinds: `routineReport`, `routineApproval`, and `routinePaused`.  Migration `0062_routine_hosts` adds each routine's approved and declined sites, the `hosts` approval kind, and drops the earlier `rio_routine_groups` ledger.

- **Making one.**  The person writes what it does and picks a schedule (hourly, daily, weekly on chosen days, or monthly, at a local time in their time zone).  Rio restates it with one model call as a plan: a summary, steps, the tables it reads and the tables it changes with approval, and what it sends to whom, with an estimate of a run's tokens, cost, and energy and carbon.  Only tables the person can see are kept.  The person saves the words, the plan, the schedule, a cost cap at or below the admin's per-run limit, and any recipient lists it may email without asking.
- **Running.**  The worker queues due routines, moving each one's next run on in the same transaction, and claims runs with `SKIP LOCKED` and a lease.  A run whose server went away is marked interrupted, never started over.  Each run acts as the owner through their access at each step: before every model call and every tool call it checks again that the routine isn't paused, that AI and routines are on for the owner, and that the owner can open the database, and stops before the step if not.  The same check reloads the routine and the AI settings, and hands its tools the saved instructions, plan, recipient lists, and sites and the autonomy rules as they are now (`RoutineTools.refresh`), so anything the owner takes back holds from the next step.  Before every model call it also takes up the cap again, the lower of the routine's own and `routineRunLimitUsd`, and the monthly budget, and resolves the model again in the same tier order, stopping the run with `routines.run.aiOff` when it's gone or its provider, model, or base URL changed.  An owner who left the organization, or who can no longer open the database, pauses the routine with a notice.  It uses the everyday model, or the power model when that's all there is, and only one whose price is known or that runs locally.
- **Tools.**  The panel's tools, held to the routine's database: `get_schema`, `find_records`, `count_records`, and `propose_changes`, plus `send_email` and `fetch_page`.  A routine makes no change on its own: every proposal becomes an approval, and nothing is written until its owner approves it, when it applies as them in its own undo group.  `routines/commands.ts` rebuilds each proposed command from the keys a routine may use (create: `kind`, `tableId`, and `records[{values}]`; update: `records[{id, values}]`; trash and restore: `recordIds`) and refuses one with any other key, such as `formViewId`, with `routines.changes.shape`.  A proposal for a table outside the saved plan's `writes` is refused with `routines.changes.notInPlan`.  Approving checks the stored commands against the same keys and the tables saved then.  Reading, and emailing the owner alone, are all a run does unattended.  Proposals are validated as the approved owner would make them.  `validate()` in `ai/plans.ts` gives its commands a simulation row-number source, as the automation simulator does, so no validation, here, at approval, or in Rio's panel, takes a number from any sequence.  Proposals are parsed with the tool's own schema (100 records a command) and capped at 200 records in all, and every `propose_changes` call, refused or not, counts toward the run's five.  A write to a signature field is refused at proposal time with `routines.changes.signature`, and the commands refuse it from any routine actor, approved or not.  The inert-change plumbing stays as defense in depth: a change made with an unapproved `actor.routine` sets off no automation, AI field run, webhook, or signature cancellation (`routineOwn`), though no path makes one now.  Routines change records only (`ROUTINE_COMMAND_KINDS`: create, update, trash, and restore).  Any other command, on its own or in a plan, is refused when proposed with `routines.changes.recordsOnly`, and the tool never offers one.  Each plan approval keeps the exact changes `routines/changes.ts` works out from its commands through the owner's access: each table and how many records, each field's values before and after, every deletion, and the open signature requests it would cancel (`signaturesCanceled`).  A change is judged by stored values (`checkCellValue` against the record's value, through `sameValue`), and a value a record already holds is dropped from the stored commands, so no command writes a field the card doesn't name.  The plan also keeps what each cell it writes held (`held`), fingerprints of the entire stored rows targeted by deletes and restores (`targets`), and the exact normalized command effects (`effects`).  Its changes come out in an order of the database's, never the command's: tables by ID, fields by position then ID, and pairs by record count then text, and at proposal they're worked out from the commands as read back from JSONB, so the same plan worked out at the click reads the same.  Each created, updated, deleted, or restored record has its own `records` row containing its primary value, record ID, and every field’s full before and after text.  IDs are shown on every row, including separate proposals for records with the same primary value.  Field summaries remain for older clients, but the current bell and card render the record rows.  Numbers show every stored digit, or their stored value beside the field's wording when it rounds, and times show seconds in the routine's time zone with the zone named.  `reveal()` shows as `\uXXXX` controls, formats, spaces other than the plain one, default-ignorable code points, the braille blank, anything NFKC changes, letters of any script the replaced value isn't written in (Latin when it has no letters), and anything outside ASCII in an email or URL, and marks runs of spaces, spaces at the ends, tabs, and new lines.  Values are compared, and counted, whole.  Two that format the same are shown with their stored JSON beside them, and characters that are invisible or could pass for others (controls, formats, odd spaces, anything NFKC changes, Cyrillic, Greek, Armenian, or Cherokee letters beside Latin ones, and anything outside ASCII in an email or URL) are shown as `\uXXXX`.  Any of these keeps a plan from being small, as does a rounded number, a pair that differs only in spacing, or an update record without a name of its own.  Legacy field summaries show pairs up to 200 characters whole, and longer pairs as the same window of each from just before where they first differ.  Record rows retain the entire values.  The existing one-click checks still require every difference to fit inside that window.  A long value a new record is given never counts as shown.  A plan is `small`, which the bell may approve in one click, only when it adds or edits 20 records or fewer, deletes nothing, cancels no request, writes only `ROUTINE_PLAIN_FIELD_TYPES` (and no AI, source, or managed field, and none another field's options or AI prompt, an automation, a record rule, or the filter or sorts of a view an automation's trigger watches names, such as a link's `match`, nor the primary field of a table a link points at, and none at all while an automation in the database has a script step), shows every change in full, lists no more than `ROUTINE_BELL_VALUES` (3) changes for any field, and the autonomy rules would let Rio make it without a preview (`canApply`).  Email to the owner goes at once, and email to anyone else waits unless its exact recipient list is approved for the routine, with outside addresses held to the owner's `reportOutsideRecipients` policy.  A page can be fetched only at an exact address in the owner's saved words, or at the root of a site the owner approved for the routine: scheme, host, and port, with the path `/` and no query or fragment.  Which record a site came from doesn't matter, so nothing tracks provenance.  `siteOrigin` in the contracts turns a value into a site, taking public DNS names only, never an IP literal, a single-label name, or a private suffix.  Sites the plan's `fetches` fields name when the owner saves are listed (`POST /api/rio/routines/sites`, read through the owner's access) for them to check, and saved in `approved_hosts`.  A site a run meets later in those fields becomes one `hosts` approval at the end of the run, and isn't fetched, or even looked up, until approved.  Skipping it adds it to `declined_hosts`, which isn't asked about again.  Fetches go through the same public-internet guard automations use, pinned to the resolved address, with no redirects.  Each address goes out at most once a run, and asking again answers from the first time, so neither how often nor in what order a run asks carries anything.  Every email sent and page fetched is kept in the run's `activity` and written to the audit log (`rio.routine.emailSent`, `rio.routine.pageFetched`).  No tool changes the routine.
- **Data, never instructions.**  The owner's words are the task, in the user message.  The schema and the plan come in the system prompt as data, and record values, page text, and every other tool result come back wrapped as data.  The guards above hold even when a model does what a record or page says.
- **Caps.**  Before each model call, the most it could cost, counting every byte sent as a token plus the output limit it's given, has to fit what's left of the cap, and the output limit shrinks to fit.  Each tool call counts toward a step cap of 20, and a five-minute time limit aborts whatever is under way, a fetch, a database tool (with a matching `statement_timeout` for proposals), or an email send included.  An email still sending when the run ends is recorded as `sending` and then settles to `sent` or `failed` in the run's activity and in `rio.routine.emailSent`, whose `outcome` says which.  Reaching one stops the run with `routines.run.costCap`, `routines.run.stepCap`, or `routines.run.timeLimit`, keeping what it did.  Each round's cost joins `ai_spend` as it happens, and each round is recorded in `ai_usage` as `routines` work with its estimated energy and carbon, which the run adds up and keeps.  The monthly budget stops a run the same way.
- **Derived effects.**  Exact routine validation retains every command-bus effect, including `record.linksChanged` on matched and inverse links.  `data/commands/preview.ts` also reads affected computed fields before and after the same savepoint, through `AccessScope`, to include lookups, rollups, counts, and formulas whose dependencies change.  These are descriptions of the original commands, never extra commands to apply.  Approval repeats validation under the database lock and compares normalized stored assignments as well as their displayed text.  Effects outside the routine’s saved write tables are refused.  More than 200 affected records, computed dependencies requiring more than 200 records in a table, inaccessible dependencies, execution-time values, repeated direct writes to one record, new records in tables with matched links whose physical order simulation cannot preserve, and unsupported effect kinds are refused with `routines.changes.incomplete`.  Validation rolls back every simulated effect and consumes no sequence values.  Deletes and restores fingerprint every target, including trashed rows and hidden stored values, without disclosing those values.  Older approvals without the new snapshots must refresh before they can be accepted.
- **Pausing.**  An owner's pause and one a routine gives itself are kept apart from an admin's (`admin_paused_at`), which only an admin lifts.  A paused routine runs by no path: the schedule skips it, Run now and Change refuse, a queued run is skipped, and what it left waiting can be skipped but not approved.  The owner can't delete an admin-paused routine, and a routine they create in a database where an admin holds one of theirs starts held too, as does one there whose instructions, plan, recipients, or sites they change.
- **Inert changes.**  A change made with an unapproved `actor.routine`, which `routineOwn` (`http/policy.ts`) reads, is skipped or refused by every consumer of record changes: `queueTriggeredRuns`, `queueAiFieldRuns` (with `queueLinked`), `queueWebhookEvents`, and `attachFiles`, which refuses to cancel a signature request (`routines.changes.signatureRequest`).  Its audit metadata says `sideEffectsSkipped: 'routineRun'`.  No path makes such a change now, since a run proposes and its owner approves, and this stays as defense in depth.  An approved plan applies with `routine.approved` set and `routineApproved: true` in the metadata, and acts as the owner's own change would.
- **Approvals and reports.**  What waits goes to the owner's notifications with none of the model's words, where the bell shows the worked-out changes, approves a small edit in one click, and sends anything else to the routine's page, which approves, changes, or skips it.  Approving runs the stored commands again through the owner's access now, as a plan does, or sends the email as written or as the owner changed it.  Approving names the plan's `revision` the client showed, and anything but the stored one is refused as stale.  It then works the plan out again, inside the transaction and after the database lock, from the stored commands and the database as it is, with the owner's access and autonomy now.  When the result, the pruned commands, any `held` value by `sameValue`, a target row fingerprint, or the normalized effects differ from what was stored, nothing is made: the approval stores the fresh changes, commands, held values, target fingerprints, and effects under the next revision and answers `routines.approval.stale`, and the app shows the plan anew.  When the recompute leaves no commands, the approval closes as skipped with `routines.approval.nothingLeft` instead.  The routine row is locked `FOR NO KEY UPDATE`, so a run adding an approval meanwhile, whose foreign key takes `FOR KEY SHARE`, never deadlocks with it.  `oneClick` approvals from the bell are held on the server to plans marked `small`, in the fresh result as well as the stored one, and to none while the owner's effective autonomy is `ask`, refusing anything else with `routines.approval.oneClick`.  The bell offers one click only when it lists every record row in full, within `ROUTINE_BELL_RECORDS` and `ROUTINE_BELL_FIELDS`, alongside the existing plain-value checks.  Every approval read or answer first checks that the owner can still open the database, and when they can't, discards everything waiting (clearing its drafts) and refuses with `routines.lostAccess`.  Changing a plan queues a revision run with the owner's note.  A new scheduled run replaces what an earlier one left waiting, and anything left expires after seven days.  Each finished run notifies its owner with who it emailed and how many pages it fetched, as the server recorded them, never the model's report, which stays on the run behind the owner's database access.  Notices saved with a report's start drop it when read.  A run that stops because its owner lost the database or left leaves no new sites waiting.  The app shows a report as plain text, never as links.  Three failed runs in a row pause the routine.
- **Admins.**  `AiSettings.routines` and the unit policy `aiRoutines` turn routines on and off, alongside AI as a whole, and `routineRunLimitUsd` caps every run.  `GET /api/admin/routines` lists every routine in the organization, with its words, plan, schedule, and recipients only in databases the admin can open, `POST /api/admin/routines/:routineId/pause` and `/resume` set and lift an admin's pause, and `DELETE /api/admin/routines/:routineId` deletes one, for admins with the AI role at the organization's scope.  Routines don't travel in an organization archive, since they act on their own as their owner.

## Plan previews

Database plans expose `GET /api/rio/plans/:planId/preview?timeZone=...`.  The route checks plan ownership, expiration, current access, and each command through the command bus in a savepoint.  It captures the resulting schema and tile data through `AccessScope`, then rolls everything back without audit, broadcast, or sequence consumption.  Record lists share a cap of 200 records across the preview.  Dashboard aggregates cover the full visible set.

The browser opens that snapshot in the Show me sandbox with a memory outbox, an inert realtime connection, and a local reader with no network fallback.  Preview uses the existing dashboard, interface, automation flow, and view components.  `rioPreview` and `rioPreviewTarget` retain the plan and selected result in the address.  Closing discards the fork.  Apply closes the sandbox before calling the ordinary plan route, which revalidates the commands and keeps their single undo group.

Automation proposals force `draftOnly` on creation and reject publication or enabled-state changes.  The shared command contract supports draft-only creation for every caller.  Existing draft columns hold the unpublished configuration, and the published configuration stays inert until publication.  Migration 0081 backfills every missing publication timestamp, including copied automations with pending drafts.  Organization archives without the `automationPublication` manifest marker receive the same backfill on import, regardless of schema version.  New automation snapshots carry `neverPublished` so undo can distinguish drafts from older published copies with empty timestamps.  Database archives retain unpublished configurations as drafts, while published copies receive a publication timestamp on insertion.  Enabling an unpublished automation is refused until a person publishes it.

Schema context lists tables and fields first, with names and IDs for dashboards, interfaces, and automations.  The get_dashboard, get_interface, and get_automation tools read one scoped object on demand.  Automation summaries omit destinations, payloads, and executable content.

Database plans retain fingerprints for existing dashboards, interfaces, and automations, including the live automation behind a button.  Apply refuses changed targets.  Command-derived approval details stay out of provider context.  Button execution always asks and names the automation and its live steps.  Restoring tables, fields, views, and interfaces stays outside the proposal vocabulary because it can reactivate public access.  External checks follow schema properties and leave record values and field-keyed maps alone.  Validation seals messaging credentials locally so previews never write remote vault entries.  Preview uses no database advisory lock and shares a five-second, twenty-read, and two-hundred-row budget.  Each aggregate has its own savepoint and refuses live tables.  Each person can start up to 30 previews per minute, with only one preview running at a time.

## Database creation

On home or without an open database, make, set-up, and tracking requests use `create_database`.
Inside a database, Rio proposes tables unless the person requests a new database.  The current
home folder travels in `RioContext.folderId`.  An omitted tool destination uses that folder,
or the person's root. Creation always waits for approval, including under instant autonomy.

`list_templates` supplies the starter catalog, blueprint schema, and key-reference guidance
on demand. A plan can use a starter or supply tables with keyed fields, views, and records.
A supplied tables array replaces the starter's tables.  Starter plans retain at most three
samples per table and add a list or calendar when useful. Links between retained samples,
select choices, formulas, and relative dates resolve into ordinary commands once at proposal
time. Both ends of each link keep reserved field IDs through preview and approval.

Pending creation plans use the existing home-capable plan row and JSON command envelope.
No database exists yet.  Preview temporarily creates the database and exercises those commands
inside savepoints, including computed sample values, then rolls back. The sample checkbox
reloads that snapshot without record commands.  Apply uses the same selection.  Folder names,
field types, views, and starter attribution appear in the existing sandbox dialog.

Creation, initial ownership, and folder placement share the creation operation used by the
ordinary database and starter endpoints. Table, field, view, and sample commands retain the
same validators, audit events, and notifications. The actor must be a member who can edit
records in the destination folder.  Folder grants then apply through normal inheritance.
Preview and approval recheck those permissions and current organization settings and budget.
Folder placement uses the move command's inherited-access check before filing the new database.
Guest access must satisfy the external-sharing policy and the database's guest-sharing rules.
The regular reply usage and footprint line cover the planning calls.

Creation previews budget two reads per proposed view, including each table's initial grid,
within the stored command limit.  This covers records and aggregates for all supported
blueprints while retaining the five-second deadline and two-hundred-row limit.

Approval saves one undo group and opens the new database.  The receipt remains available after
reloading the conversation.  Undo uses the existing command reversal to remove the whole
database from home and make it unavailable, with the usual Trash retention and redo semantics.
No migration is required.
