# Organization archives

The organization archive is a streamed, stored-entry container.  It uses the database archive contract for each database's schema and adds a sequence of catalog and physical rows so records can be read and restored without assembling a database's records in memory.  Each database has one entry.  Attachment contents are separate entries, and the organization manifest lists every payload entry's SHA-256 hash and length.

## Container

The byte stream starts with `RIOSOMA-ORG-1` and a newline.  Each entry has a 44-byte header containing a four-byte unsigned name length, an eight-byte unsigned content length, and a 32-byte SHA-256 digest, all integers in big-endian order.  The UTF-8 name and content follow.  A zero-filled header ends the stream.  Trailing bytes, duplicate names, unknown entry names, incomplete entries, and incorrect hashes are refused.  Only stored entries are accepted, so there is no compressed payload to expand.  Archive names are never used as filesystem paths.

Entries are `organization.jsonl`, `databases/<database ID>.jsonl`, `files/<attachment ID>`, `templates/<template ID>.json`, and `manifest.jsonl`, which comes after them.  With a passphrase, `manifest.hmac` and `secrets.jsonl` follow the manifest, in that order, and nothing else may.  The manifest's first line is the organization summary and schema version.  Later lines list the name, length, and hash of every entry before it.  These hashes detect corruption, not a deliberate change: anyone can recompute them.

`CATALOG_PLAN` in `catalog.ts` lists every catalog an archive carries, the entry it's written to, and how an import restores it, in the order an import restores them.  Export writes those catalogs and no others, and import walks the same list.  Every other table in the app schema is in `LEFT_OUT` with its reason, such as personal calendar subscriptions, custom domains, sessions, OAuth grants and tokens, and run history.  A test fails when a table after migrations is in neither, when a name in either isn't a table, when a catalog has no way back, or when the plan restores a catalog before one it refers to.  Signers are outside the organization, so their IP addresses and browsers are taken out of exported audit events.

JSON lines are read as bytes, each chunk searched once from where the last search stopped, so a long line costs time in proportion to its length.  A record's line or a template over 64 MB is refused with `organizationArchive.tooLarge`, and so is a catalog line over 16 MB, since catalog rows are held whole for the preview.  A byte scan follows the nesting outside strings as each chunk arrives, so a value nested more than 128 arrays or objects deep is refused as soon as it passes the limit, before anything parses it.

## Authentication and secrets

Without a passphrase the archive is unauthenticated, and the preview says so.  With one, Argon2id version 19, with a random 16-byte salt, 65,536 KiB of memory, three iterations, one lane, and a 32-byte output, derives a master key.  HKDF-SHA256 over it, salted with the same salt, derives two separate keys: one for encryption and one for authentication.  Import accepts only that bounded profile.

`manifest.hmac` is the HMAC-SHA256 of the manifest's bytes under the authentication key.  Since the manifest lists every other entry's SHA-256, the HMAC covers the whole archive.  The manifest can't list the HMAC or the secrets, since both depend on it.  Each line of `secrets.jsonl` names, in the clear, the entry, catalog, row identity, column path, and old sealing context of one credential, and seals its value with AES-256-GCM under the encryption key.  Its associated data is those same fields and the manifest's HMAC, so a secret opens only in this archive and only at the place it names.  A catalog line lists the paths the export took credentials out of, whether or not it carried them, and a secret line must name one of them, once.

Nothing is shown as trusted or restored until the HMAC and every secret check out.  Checking the passphrase before confirming reads the stored archive once, hashing every entry but keeping only the manifest, its HMAC, and the secrets.  Confirming checks again against the full archive.  A wrong passphrase and a changed archive look the same, and both leave the upload waiting, with nothing written.

Credentials are sealed values, text whose name says it's a credential, a web address's user name and password, and query values with credential-like names.  Configuration that sends somewhere, meaning automation step settings, source connections (file and feed addresses included), and webhook addresses, counts every web address in it as a credential whatever its parts: the whole text is sealed, and the clear copy keeps only each address's scheme and host, which the review list shows.  So does a string value in a JSON body whose member is named like a key, token, secret, password, or signature, in any case.  In automation steps every header value counts as a credential too.  Only text is ever a credential, so flags such as `secretSaved` travel as they are.  Restored credentials are sealed again with the destination's instance key and the new IDs.  Sign-in providers, AI provider keys, and the server's own settings are never exported.

## Import

Export reads one repeatable-read snapshot.  Temporary files provide backpressure and entry hashes, then one-megabyte PostgreSQL chunks retain the finished archive across restarts and replicas.  Working folders live in one folder, `RIOSOMA_ARCHIVE_WORK_DIR`, by default `riosoma-archives` under the system's temporary folder, which only the server's account may enter.  Each is made with mode 0700 and named `rio-organization-<process ID>-<process start>-<made at>-`, both times in milliseconds.  Servers may share the folder, so a process ID and its start say who owns each one.  At startup a server never removes a folder whose owner is still running, and removes the ones whose process stopped or whose process ID now belongs to a process that started at another time.  A folder no live process can be shown to own, because its name doesn't say or the system can't say when a process started, goes once it's 24 hours old.  A folder named before names recorded a process's start is dated by its own creation and change times: it goes when its process stops, when it was made before that process started, or once it's 24 hours old.  A process's start comes from `/proc` on Linux and from the process listing, read in UTC, elsewhere.  Each test server has a folder of its own, and so does each test file's own archive work.

Import stages and inspects the complete stream before showing a preview, then does so again at confirmation.  Inspection parses every line and template, refuses a catalog row with any column its table doesn't have on this server, and an authorship row naming a column its catalog lacks, checks that the organization's name in the manifest is the one written, and refuses audit events dated more than five minutes ahead of the server's clock.  A passphrase sent for an archive without an HMAC is refused with `organizationArchive.unsigned`, rather than ignored.  The entire organization commits in one transaction, a stronger guarantee than separate database transactions.  The final report commits with that transaction.  Export archives expire seven days after completion.  Abandoned jobs fail after their heartbeat expires.

Only organization settings on an allowlist are restored.  AI settings come in off, with no providers and only their model choices.  Files go through upload finalization: the type comes from the content, the file is quarantined when a scanner is set, and previews are made again.  The archive's type and scan state are ignored.  Audit events are inserted dated at the import, with no actor, and with `imported`, `originalAt`, and `originalActorId` in their metadata.

Deterministic keyed ID remapping gives records new IDs without retaining a map entry per record.  An ID changes only where the schema puts one: a whole value or key that is an ID, a `{{…}}` token, a field named in braces as formulas, AI prompts, and button links do, a comment's mention, and the row a sealing context names.  Free text and web addresses keep every character, so an outside identifier that looks like one of ours stays as it was.  The importing owner's email maps to the existing owner, the organization's only owner.  Everyone else waits in `organization_import_review` with a reserved ID, as a member, or a guest if they were one, and with the groups they belong to.  The owner sends invitations from there, and an invitation's reserved ID keeps their shares, record values, and authorship pointing at them.  Accepting joins their groups and credits their authorship.  A new invitation never takes a kind or roles from an imported one, and takes its reserved ID only from one that's still live.  Group and folder access comes from `AccessScope`, as it does for everything else, so a group's roles never reach a guest.

Everything that reaches outside comes in off and waits in the same review list with where it goes: sources stay paused, webhooks and automations disabled, booking pages off, OAuth registrations paused, calendar feeds and feedback to a repository off, cloud drive apps disabled, and public links and forms aren't created at all.  Turning one on is the owner's choice, and only the review list does it: while an item waits there, the webhook, automation, booking page, calendar feed, feedback, and cloud drive app settings refuse to turn it on with `organizationArchive.review.turnOnFromReview`, through the API with a token too.  An automation turns on through the command bus as the owner, once no step still lacks the credential the import left out, with its review item marked done in the same transaction.  A paused source has nothing unsealed and reaches nothing, whatever its sign-in method: every connector path, live reads included, takes one function that refuses it.  A paused webhook source refuses every post, and gets a new incoming address only when the owner turns it on.  A source needs its credentials first, and a source or webhook whose address came with only its scheme and host needs the address entered again.  An archive imported without its passphrase restores no credential of any kind: sources' secrets, webhook signing secrets, messaging credentials, cloud drive app secrets and keys, the feedback token, and public link passwords are all left empty, whatever the archive holds, and turning feedback on checks that a token sealed here is set.  Public links and forms get new addresses, and a webhook source a new incoming address.
