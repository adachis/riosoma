# SQL access

Each database has a SQL screen for querying its stored PostgreSQL tables.  Organization owners and security administrators choose which database roles can use it under **SQL administration**.  The default is owners only.  Access still requires a database role, and SQL never grants access to another database.

## Editor settings

Settings are stored per database and take effect on the next run.  They do not need environment variables.

| Setting | Default | Accepted values |
|---|---|---|
| Roles allowed to use the SQL editor | Owner | Any selection of owner, creator, editor, commenter, and reader |
| Query timeout in milliseconds | 15,000 | 10 through 120,000 |
| Maximum result rows | 10,000 | 1 through 100,000 |

The server parses one SELECT with the PostgreSQL grammar from the MIT-licensed `libpg-query` package.  The package ships WebAssembly and needs no native installation build.  The guard accepts only classified syntax and explicitly allowed functions, operators, and casts.  It rejects writes, SELECT INTO, row locking, multiple statements, schema names, catalogs, settings access, file functions, network functions, and unclassified syntax.

Every column reference must resolve to a column of a table, WITH query, or subquery in scope.  PostgreSQL reads `p.name` as a call of the function `name` on the whole row when `name` isn't one of p's columns, so the guard refuses a reference it can't resolve rather than leave it to PostgreSQL.

The query executes inside a read-only transaction on connections kept for SQL editor queries, apart from the pool the rest of the app uses, so long queries never hold up other requests.  There are three by default, set with `RIOSOMA_SQL_POOL_MAX`, and a query waits up to 15 seconds for one to come free.  Each person runs one query at a time and starts at most 30 a minute.  Each server process has its own connections and counts on its own, so allow for these connections when sizing the database's connection limit.  It runs as a dedicated PostgreSQL role, `rio_query_` followed by a hash, when that role is available.  The role has no login and no memberships, and can read the data schema's tables plus the person and file names that permission rules and link names use.  It can change nothing and read nothing else.  If the application account can create roles, Riosoma creates the role and grants it these privileges.  Otherwise **SQL administration** shows the SQL for a PostgreSQL administrator to run, and queries run with the application account's privileges until then, still limited by the guard and the permission projections.  Riosoma checks the role at most once a minute.  The search path is empty, leaving PostgreSQL's built-in catalog resolution, and every stored table reference is replaced by a permission projection.  A projection contains only visible fields and permitted records.  Locked fields remain readable.  An optimization boundary keeps user expressions outside record filtering.  Database errors are translated without forwarding details, hints, or physical names.

Results are capped before they are returned, with a further 32 MiB result limit.  Date-only fields come back as `YYYY-MM-DD`, whatever the server's time zone.  Reported durations are rounded to the nearest 100 ms.  SQL access can still reveal roughly how many records a table holds, including records a rule hides, through query timing, so give it only to roles that may know that.  The SQL screen pages through 100 rows at a time.  The server keeps the person's 50 most recent queries and results, and rechecks the permission projection before another page or download.  Changed access expires old results.  Every attempted query by an authorized SQL reader records its query text, returned row count, duration, and error key in the audit log.  Treat query text as organizational data when setting audit retention.

## Friendly names

Use the quoted names offered by the catalog and autocomplete.  Names are case sensitive when quoted.  A duplicate, reserved name, or name longer than PostgreSQL's 63-byte identifier limit uses its stable ID instead.  Restricted fields are absent, including their friendly and physical names.  Links contain a `records` array and a `hiddenCount`, matching the API's visible IDs and hidden-record count.  Numeric SQL results retain PostgreSQL's precision, so large integers and decimals can appear as text.

Live-source tables are excluded because their local mirrors are incomplete.  Copy-synced tables are available.  Supported syntax includes joins, nested WITH queries, recursive WITH queries, subqueries, set operations, aggregates, and window functions.  Unclassified extensions remain unavailable.

## Automatic outside login

Outside logins are off until whoever runs the server sets `RIOSOMA_SQL_OUTSIDE_LOGINS=on`.  While the setting is off, **Enable login** and **Rotate password** are refused, and a login that was enabled earlier is turned off within about five seconds: its views stop returning rows, its connections are ended, its schema and role are dropped, and `databases.sql.loginDisabled` is recorded in the audit log with the reason `notAllowed`.  Each login is turned off on its own, so one that can't be removed yet holds up no other.  If the application account can't drop the role, **Outside tools** shows the cleanup SQL.

The setting is the server's because an outside login connects to the same PostgreSQL database as every organization on the server, and PostgreSQL shows every role its catalogs.  Read [What an outside login can still see](#what-an-outside-login-can-still-see) before turning it on.

An administrator selects an active Riosoma person in **Outside tools** and chooses **Enable login**.  The login reads as that person, including their database role, restricted fields, record rules, and linked-record rules.  Sharing the password shares that person's access to this database.

Nobody widens their own access.  An administrator can choose a person other than themselves only when no field rule or record rule limits the administrator's own access to that database.  Otherwise the only choice is themselves.  **Rotate password** hands out a password too, so it follows the same rule for whoever rotates.  Every rebuild checks again against the administrator who last enabled or rotated the login.  If the chosen person's access has grown past that administrator's, the rebuild turns the login off, removes its views, and records `databases.sql.loginDisabled` in the audit log.

Each login is a dedicated PostgreSQL role with a friendly view schema.  Riosoma creates both itself when its application account is a PostgreSQL superuser.  Any other account, including one that can create roles, shows the administrator SQL instead, because part of setting a login up takes a superuser, as described below.  The login has no elevated role attributes or memberships, no base-table permissions, and SELECT permission on its views.  Views use PostgreSQL's security barrier.  The login's default transaction mode is read only, its default search path points to its view schema, and its default statement timeout follows the editor setting.  A PostgreSQL client can change those defaults for its session, and a role can change its own for good, for every database or for this one alone, so none of them is a limit.  Riosoma puts them back at the next rebuild, in both forms, when its application account may alter the role.  What holds is what privileges refuse and what the server does about a login's connections:

- **No advisory locks.**  The server serializes its own work on advisory locks, so a login that could take them could hold up every change to a database, the audit log, or the next upgrade.  Setup takes EXECUTE on the functions that take an advisory lock away from PUBLIC and grants it to the application account.
- **No temporary tables, and a limit on temporary files.**  Setup takes TEMPORARY on the database away from PUBLIC and grants it to the application account.  It also sets `temp_file_limit` to 1 GB on the login's role, which caps what one connection's sorts and joins write to disk.  Only a superuser can set or change that limit, so the login can't lift it.  PostgreSQL counts the limit per process, and a query can start parallel workers that each have their own, so the most the login's temporary files can hold is 1 GB times the sum of its 10 connections and the server's `max_parallel_workers`.
- **No large objects or log messages.**  PostgreSQL lets every role create large objects and write messages to the write-ahead log.  Both stay on disk, and neither the read-only default nor the temporary file limit covers them.  Setup takes EXECUTE on the large object functions and on `pg_logical_emit_message` away from PUBLIC and grants it to the application account.
- **No view text.**  A view's text holds the permission rules of the person it reads as, with their values.  Setup takes EXECUTE on `pg_get_viewdef` and `pg_get_ruledef`, and SELECT on `pg_catalog.pg_rewrite`, away from PUBLIC and grants them to the application account.  `pg_views` and `information_schema.views` then refuse to show a definition to the login.
- **Connections the server can end.**  A connection that reads a view holds a PostgreSQL lock on the view and on the tables it reads until its transaction ends, and it can keep that transaction open.  So Riosoma opens a login only when it can end the login's connections, which PostgreSQL allows a superuser or a member of the login's role.  Setup makes the application account a member of each login's role.  It also refuses to open a login while the PostgreSQL server allows prepared transactions (`max_prepared_transactions` above 0), because a prepared transaction keeps its locks after its connection ends.  See [When Riosoma ends a login's connections](#when-riosoma-ends-a-logins-connections).

The changes to PUBLIC apply to the whole PostgreSQL database, and changing the privileges of built-in functions takes a PostgreSQL superuser.  When the application account is a superuser, Riosoma makes them itself the first time a login is enabled.  Otherwise the login stays closed, **Outside tools** says why, and the administrator SQL includes the statements for a superuser to run.  On a managed PostgreSQL service whose administrator account is not a true superuser, PostgreSQL can refuse those statements, and outside logins then stay closed.

Any other role that takes advisory locks, creates temporary tables, uses large objects, or reads view definitions in this database, such as a separate backup account running `pg_dump`, needs the same privileges granted to it by name.  The grants name the application account that was connected when the SQL was shown.  If you later connect Riosoma as a different account, grant that account EXECUTE on the advisory lock functions and TEMPORARY on the database first, or its changes fail.

Riosoma checks all of this again whenever it rebuilds a login's views, and on every refresh while PUBLIC still holds any of these defaults, a login's role has no temporary file limit, or the application account is not a member of a login's role.  That is how a login created by an earlier version stands after an upgrade.  A superuser application account fixes it at the first refresh and the login stays open.  An account that created the login's role joins it at the first refresh.  Any other account closes the login until the administrator SQL has run, then reopens it within about five seconds.

A connection that was open before any of this changed keeps what it had: PostgreSQL applies the temporary file limit when a connection starts, and a connection keeps the advisory locks and temporary tables it already took.  So Riosoma ends the login's connections once when it gives a role its limit, and every login's connections once when it takes a default away from PUBLIC.  The administrator SQL ends the login's connections after it commits, for the same reason.

### When Riosoma ends a login's connections

Nothing that closes a login waits on one of its connections.  Every view reads its login's state first, so a login that is turned off, or whose views are due a rebuild, returns no rows from the moment that change commits, whatever locks its connections hold.  Riosoma then ends connections to take the locks back:

- **Turning off and rotating.**  **Turn off login**, **Rotate password**, enabling again, and the server setting going off end every connection of the login.  They end them again once the change has committed, because a tool that reconnects at once would otherwise be back under the old password.  **Check** does the same for a login that was closed.
- **Trash and deletion.**  Moving a database to the trash, deleting a database for good, and deleting the login's person or the administrator who enabled it turn the login off and end its connections.
- **No role.**  PostgreSQL drops a role while connections of it are open, and a tool that reconnects while its login is being removed can be left connected with no role.  Such a connection has only what PUBLIC has, and no login to end it by.  Every five seconds, Riosoma ends every connection to its database whose role no longer exists.  PostgreSQL allows that to a superuser or a member of `pg_signal_backend`.  If the application account is neither, grant it `pg_signal_backend`, or these connections stay until they close or a PostgreSQL administrator ends them.  The cleanup SQL ends them as its last statement.
- **Rebuilding.**  A rebuild waits about a second for a connection that is reading a view, then ends the login's connections that are inside a transaction.
- **Holding up other work.**  Every five seconds, Riosoma ends a login's connection that holds a lock another session is waiting for, such as a change to a field of a table the connection read.  At startup it does the same every two seconds while migrations run.
- **Running or idling too long.**  Every five seconds, Riosoma ends a login's connection whose statement has run longer than the database's query timeout plus five seconds, which a client reaches only by lifting the statement timeout.  It also ends one that has sat idle inside a transaction for that long, because an open transaction keeps its locks and holds back PostgreSQL's cleanup.  A transaction that keeps working, such as a tool reading a large result in batches, stays.
- **Holding back notifications.**  A connection that listens inside a transaction keeps PostgreSQL from clearing its notification queue, and a full queue fails every change the server makes.  When the queue is more than 5 percent full, Riosoma ends every login's connection that is inside a transaction.

Set reporting tools to autocommit, so each query is its own transaction, and expect them to reconnect after any of these.

### What an outside login can still see

Use a PostgreSQL database dedicated to Riosoma, and turn outside logins on only when everyone who will hold one may know the following.  PostgreSQL has no privilege that hides these from a role that can connect.

- **Names.**  The catalogs list every schema, view, and column, so a login can read the table and field names of every database that has an outside login, in every organization on the server.  It can't read their records or their view text.
- **Counts.**  Table statistics and sizes are open to every role, so a login can see roughly how many records every table on the server holds.  Tables outside its own views appear under their internal IDs.
- **Its own rules.**  `EXPLAIN` on the login's own views shows the record rules of the person it reads as and how many records they filter out.
- **Time and memory.**  The statement timeout, like `work_mem`, is a session default the client can change.  Riosoma ends a connection within about ten seconds of a statement outlasting the query timeout, so no query runs for long, but until then a login can run heavy queries on up to 10 connections, and it can reconnect and run them again.  Give a login only to people and tools you would trust with that.
- **Other databases on the same PostgreSQL server.**  PostgreSQL lets every role connect to any database on which PUBLIC still holds CONNECT, which is the default, and everything setup takes away from PUBLIC is taken away in Riosoma's database only.  In another database a login has whatever PUBLIC has there, which by default includes temporary tables and large objects, so it can see that database's names and fill disk.  Riosoma does not check this.  Use a PostgreSQL server dedicated to Riosoma, or keep outside logins out of its other databases with `pg_hba.conf` or by revoking CONNECT on them from PUBLIC.
- **Notification channels.**  Every role can listen and send on PostgreSQL's notification channels.  Presence notices, which say who is viewing or editing what, are sealed with the instance secret key, so a login can neither read them nor forge them.  The other channels carry only IDs.  A login can read those IDs, and can send notices that make servers recheck access and browsers reload lists, which costs work and changes no data.  A login that listens while it keeps a transaction open also holds back the cleanup of PostgreSQL's notification queue, until Riosoma ends its connection, which it does once the transaction sits idle too long or the queue starts to fill.

Use the PostgreSQL server's connection address, database, port, and TLS settings in the BI tool, together with the displayed login and password.  The database administrator must permit that connection through the network and PostgreSQL authentication configuration.  Riosoma verifies the credentials through its database connection settings.  Save the password when it is displayed.  Pending credentials are sealed with the instance secret key, and provisioning SQL contains a SCRAM verifier, not the plaintext password.

## Installation without role creation privileges

The app and editor work when the application account owns only its existing schemas and has no CREATEROLE privilege.  Outside setup then stays closed and shows the exact provisioning SQL for a PostgreSQL administrator.

1. Choose the person and enable the login in Riosoma.
2. Save the displayed password.
3. Have a PostgreSQL administrator run the displayed SQL in the application's PostgreSQL database.  It creates or alters the login and creates a view schema owned by the application account.
4. Choose **Check**.  Riosoma checks role attributes, memberships, object privileges, view-schema ownership, and the connection before building views.

The displayed SQL also takes the PUBLIC defaults described above away, sets the role's temporary file limit, and makes the application account a member of the login's role, so a PostgreSQL superuser must run it the first time, and whenever it creates a new login's role.  An application account that can create roles but is not a superuser is in the same position: it creates nothing by itself, and the login waits for this SQL.  The SQL's last statement, after its COMMIT, ends the login's connections, so run all of it.

Check refuses roles with access to other application tables, writable columns, sequences, schema creation, database creation or temporary-table privileges, advisory lock functions, large object functions, view text, no temporary file limit, connections the application account can't end, or executable security-definer routines outside the system schemas.  It refuses every role while the PostgreSQL server allows prepared transactions.  This includes access inherited from PUBLIC.  A database administrator must remove incompatible grants and preserve access for other applications through explicit roles.  Use a database dedicated to Riosoma.

PostgreSQL 14 grants CREATE on the `public` schema to PUBLIC by default, so every role can create objects there.  Both editor-role setup and outside-login setup revoke that grant when the application account has the privilege, using `REVOKE CREATE ON SCHEMA public FROM PUBLIC;`.  This preserves USAGE and explicit grants to other roles and adopts PostgreSQL 15's default for new databases.  Upgraded databases can retain the old grant on newer versions, so setup checks the actual privileges on every supported version.  When the application account cannot revoke it, SQL administration explains why setup is not ready and includes the revoke statement in the administrator SQL with a one-line explanation.  Run that SQL as a PostgreSQL administrator and choose **Check** for the outside login.  Incompatible PUBLIC grants other than the ones setup removes remain the administrator's responsibility.

## Changes, rotation, and shutdown

Migration `0040_sql_access` adds settings, query history, login state, and invalidation triggers.  Field, rule, role, membership, source, link, user-deactivation, and database-trash changes close affected outside views within the change transaction: the views return no rows once the change commits.  The same transaction also removes the views, unless a connection of the login is reading one at that moment.  Migration `0131_sql_views_give_way` makes that removal give way at once instead of waiting for the connection, so a login can't hold up changes to fields, rules, or memberships anywhere on the server.  It also makes deleting a person end the connections of that person's login before it drops the login's role.  A worker rebuilds enabled, verified logins within about five seconds, each in a transaction of its own.  A failed rebuild leaves access closed.  The first implementation conservatively invalidates all configured outside views on an access-related metadata change.

Deleting a person for good, whether the person a login reads as or the administrator who last enabled or rotated it, turns the login off in the same transaction, ends its connections, removes its views, and drops its schema and role.  It records `databases.sql.loginDisabled` in the audit log with the reason `deleted`.  If a connection of the login is reading a view at that moment, the login is still off, and the worker ends the connection and finishes the removal within about five seconds.  If the account deleting the person can't drop the role, or can't end one of its connections, the login stays off with its cleanup SQL shown in **Outside tools** until a database administrator runs it and an admin chooses **Check**.

Moving a database to the trash turns its login off within about five seconds, the same way **Turn off login** does, and records `databases.sql.loginDisabled` with the reason `trashed`.  Restoring the database does not bring the login back: enable it again, and give the new password to whoever needs it.  Deleting a database for good removes whatever is left of its login first, with the reason `purged` if the login was still on.

A login never keeps its role longer than Riosoma keeps a record of it, because that record is what Riosoma ends the role's connections by.  If a role is ever left without one, as an earlier build left it when a database with a login was deleted for good, Riosoma knows it by its schema, named `rio_sql_` and 24 hexadecimal digits and owned by the application account.  Every five seconds it ends that role's connections, and it drops the role and schema when the application account may.  When it may not, a PostgreSQL administrator drops the schema and the role named `rio_read_` and the same digits.  Riosoma looks for these only while no other Riosoma install keeps its tables in the same PostgreSQL database, since that install's logins are named the same way.

Relative date rules use UTC days.  Views stop returning rows at the next UTC day until the worker refreshes their predicates.  A statement already running when a change commits finishes on what it could read when it began, unless Riosoma ends its connection first.

**Rotate password** immediately closes the views, ends the login's connections, generates a new password, and attempts the role change.  In a minimal-privilege installation, run the new administrator SQL and choose **Check**.  **Turn off login** closes the views immediately, ends the login's connections, and attempts to drop the schema, what the role owns, and the role.  If PostgreSQL requires an administrator, the displayed cleanup SQL completes removal.  It ends the login's connections first and again just before it drops the role, and after its COMMIT it ends any connection left with no role.  Until the role is dropped it can still connect, though Riosoma ends its connections every five seconds, and it sees what [an outside login can still see](#what-an-outside-login-can-still-see), so run the cleanup SQL promptly.  The cleanup SQL removes what the role owns in this database.  A role that owns something in another database on the same PostgreSQL server can't be dropped until a database administrator removes that too.
